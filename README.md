# 智径 EduPath · 多 Agent 自适应学习平台

> 把「我该学什么」这件事交给它，你只管把东西看懂。

**528 张原理卡** · **821 节点 / 2715 边知识图谱** · **4 种间隔重复算法（当前默认 FSRS-6）** · **网页端 + 微信小程序**

每张卡只回答三个问题：**它是什么 / 它怎么跑 / 面试官会怎么问**。
中间那栏是机制步骤，不是一句定义 —— 看得懂定义、答不出步骤，是「背过」和「学懂」的分界线。

## 它解决什么问题

| 真实痛点 | 产品里的对应能力 |
|---|---|
| 资料读完了，合上就忘，不知道明天该看哪一页 | 复习队列由间隔重复算法排期，每天只给「今天该看的」，逾期久的自动优先 |
| 知识散在十几个笔记软件里，看不出结构 | 卡片带 `领域 → 科目 → 主题` 三级路径，同时投影成 MOC 知识框架和可下钻的知识图谱 |
| 「我会了」是感觉，不是数据 | 每次自评（不会 / 模糊 / 会）写回记忆模型，掌握度由 BKT 给出概率，而不是进度条 |
| 学完仍然答不出面试追问 | 每张卡固定带「面试官会怎么追问」，错题本按追问口径回收 |
| 手上有现成资料，但整理成可复习的卡片要花几倍时间 | 上传 md/txt/pdf/docx，Agent 精修分章 → 内容解析报告 → 勾选 → 一章出一张卡；GitHub 上现成的问答资料走确定性的题库导入，不消耗 AI |

一句话：**输入是资料，输出是「今天该复习什么」，中间的人工整理环节由 Agent 承担，但每一道关口都留了人工确认。**

## 核心闭环

```
① 导入资料        粘贴文本 / 上传整份文档 / 现成题库
      ↓           Agent 精修分章 → 解析报告 → 勾选确认
② 生成原理卡      类比 · 机制步骤 · 业务场景 · 面试追问 · 图注
      ↓           字段不齐不许入库（硬规矩，防脏数据）
③ 组织成结构      分类树（领域→科目）+ 知识框架 MOC + 知识图谱（语义边 + 层级边）
      ↓
④ 算法排程        FSRS-6 预测留存 → 算下次复习时间；BKT 估掌握度 → 排优先级
      ↓
⑤ 每日复习        今日到期队列，自评三档，进度写回
      ↓
⑥ 回写与自诊断    掌握度色条 / 岗位知识地图覆盖率 / 错题本 —— 决定下一轮学什么
      ↺ 回到 ①，缺口驱动新的导入
```

闭环的关键不在「有 AI」，而在 **②→③→④ 之间没有手工整理**：卡片的分类、路径、关联关系在生成时就带上，所以导入一百张卡之后图谱和复习队列是自动成立的。

## 架构

```
        ┌─────────────────────────────┬──────────────────────────┐
        │  网页端 web/                 │  微信小程序 miniapp/      │
        │  Vue 3 + Vite + Pinia        │  原生小程序                │
        │  Element Plus · ECharts 图谱 │  /api/mini/* 分页契约     │
        │  PWA（离线壳）               │                           │
        └───────────────┬─────────────┴────────────┬─────────────┘
                        │  https（同源或跨域白名单）  │
        ┌───────────────┴──────────────────────────┴─────────────┐
        │  后端 back_study/  FastAPI（端点写同步 def，线程池执行）  │
        │  app/routers/{web,mini}/   按端分包，跨端逻辑共用 core/  │
        ├────────────────────────────────────────────────────────┤
        │  算法层 algo/   SM-2 · FSRS-6 · HLR · BKT · Load Balance │
        │  编排层 agent/  卡片 Agent（LangGraph，可选依赖）        │
        │  数据层 core/db/  卡片 · 进度 · 图谱 · 报表 · 掌握度      │
        ├────────────────────────────────────────────────────────┤
        │  存储层 core/store/  ← 可插拔，业务代码不感知            │
        │    jsonfile.py（默认，也是降级目标）│ mysql.py（MySQL 8） │
        └────────────────────────────────────────────────────────┘
                        │
        ┌───────────────┴───────────────────────────────────────┐
        │  模型通道 core/llm.py                                  │
        │    AI=off  │  云端 OpenAI 兼容  │  本机 Ollama（默认） │
        └───────────────────────────────────────────────────────┘
```

**为什么前后端分开部署**：静态前端发布到 Qoder Sites（免运维、全球 CDN、一条命令更新），
业务后端与数据放在自己的阿里云轻量服务器上（要跑 PDF 解析、图片存储、MySQL、可选的本地模型）。
两边分开就必须解决跨域，做法是后端 `allow_origin_regex` 放行 `*.qoder.website` 与本机源，
前端用 `VITE_API_BASE` 决定打哪儿；`edu.312783.xyz` 则把 dist 与 API 挂在同一域名下，
作为「不依赖跨域」的备用入口。**任何一个宿主挂了，另一个入口还能用。**

**为什么存储层要做成可插拔**：不是为了炫技。真正值得上数据库的只有一处 ——
今日到期队列（文件后端要把全部卡读进内存逐张比对再排序，库里是一条带索引的
`LEFT JOIN + ORDER BY`）。但业务代码不应该因为换了存储就改动，所以契约收在
`core/store/base.py`。附带一条纪律：**降级必须看得见** —— MySQL 连不上会自动回退到
JSON 并照常服务，但启动横幅会打 `!!` 告警、`/api/storage` 的 `degraded` 字段写明原因；
内置卡的内容指纹对不上时报 `stale` 并回落到文件，绝不端出「源码已改、库里还旧」的版本。

## 算法与数据

调度算法在 `back_study/algo/`，换算法只改配置里一行 `ALGO`。

| 算法 | 回答什么 | 特点 |
|---|---|---|
| **FSRS-6**（当前默认） | 什么时候再看 | 记忆稳定性模型，能预测留存概率。权重与公式逐字对照 py-fsrs v6.3.3；复习记录攒够 400 条后可用 `POST /api/review/fit-fsrs` 拟合**个性化 21 权重**（SPSA + Adam，纯标准库实现） |
| SM-2 | 什么时候再看 | 纯规则，零数据可用，配置缺失时的回落值 |
| HLR | 什么时候再看 | 半衰期回归，评测里期末留存最高 |
| BKT | 到底掌握没 | 贝叶斯知识追踪，输出掌握度概率，**不排期**，用来排优先级 |

**四算法对拍**（仿真口径：300 张卡 × 365 天，同一条遗忘曲线、同一个随机种子，
`python back_study/algo/demo.py --eval` 可复现）：

| 算法 | 复习次数 | 次/卡 | 期末留存 | 掌握卡数 | AUC | RMSE(bins) |
|---|---|---|---|---|---|---|
| sm2 | 11783 | 39.28 | 56.4% | 120 | — | — |
| fsrs | 13721 | 45.74 | 63.0% | **177** | 0.526 | 0.1752 |
| hlr | 14317 | 47.72 | **66.5%** | 192 | 0.507 | 0.1223 |

- RMSE(bins) 用 srs-benchmark 现行主指标口径（对数网格三特征分箱），与官方指标对齐。
- 「—」是能力边界不是缺数据：SM-2 没有概率模型，BKT 的 p 是掌握度而非留存率。
- ⚠️ **局限必须自己先说**：仿真评测的 ground truth 是人为设定的遗忘曲线，
  结论只在「相对比较」意义上成立。真实日志评测走 `python back_study/scripts/eval_real.py`
  （用自己的复习事件流算 log-loss / RMSE(bins) / AUC），这条链路已经就位，等真实数据量长起来。

另有 **Load Balance**（默认关）：到期卡在同日过载时自动推迟到相邻闲日，
避免「今天 300 张、明天 0 张」；实现是确定性的，不引入随机源，因此不破坏双存储逐位对照。

## 技术栈与选型理由

| 层 | 选择 | 为什么 |
|---|---|---|
| 前端 | Vue 3 + Vite + Pinia + Element Plus | 状态多（卡片、进度、图谱、会话），需要显式 store；组件库省掉自研表单/表格 |
| 图谱渲染 | ECharts graph（固定 canvas 渲染器） | 早期是自绘 Canvas 粒子场，效果炫但几百节点必掉帧，且 tooltip / 缩放 / 图例要各写一套；ECharts 的 force 用四叉树近似斥力，几百点都稳。渲染器不能选 SVG —— 节点数一多 DOM 撑到几千，交互直接卡住 |
| 后端 | FastAPI + uvicorn | 要 Pydantic 参数校验和自动交互文档；端点写同步 `def`，FastAPI 自动丢线程池，避免同步 IO 卡住事件循环 |
| 鉴权 | pbkdf2 + PyJWT | 不引第三方 auth 框架，标准库 + 一个 JWT 库够用，测试里有伪造 token 用例 |
| 数据 | `data/*.js` 严格 JSON 字面量 | JS 和 Python 都能直接读，卡片数据是「唯一真相源」，不需要为两端各转一份 |
| 存储 | JSON 文件 / MySQL 8 可插拔 | 见上文架构 |
| 模型 | 本机 Ollama（默认）/ 云端 OpenAI 兼容 / `AI=off` | 离线免费能跑是底线；1 核 2G 的服务器跑不动 7B，就关云端补 |
| 编排 | LangGraph（可选依赖，仅卡片 Agent） | 只有「多步、有分支、要维护状态」的环节才值得编排；单次抽取不引框架 |
| 小程序 | 微信原生 | 体验版分发，不背跨端框架的构建链 |
| 部署 | Qoder Sites + 阿里云轻量 + nginx + systemd + MySQL | 静态前端交给平台，动态后端自己攥在手里 |

## 三分钟跑起来

```bash
# 后端（Python 3.10+）
pip install -r back_study/requirements.txt      # fastapi / uvicorn / PyJWT 必需，pymysql / pypdf 可选
python back_study/run.py 8080                   # http://127.0.0.1:8080

# 前端（Node 18+）
cd web && npm install && npm run dev            # 开发期走 vite 代理
cd web && npm run build                         # 产物在 web/dist，可直接静态托管

# 不用数据库也能跑：默认单文件 JSON 存储，改代码一行都不用
# 想用 MySQL：back_study/config.local.json 里把 STORE 改成 "mysql"（该文件不进版本库）
python back_study/scripts/dbseed.py --status    # 看现在连的是哪个存储
python back_study/scripts/dbseed.py --sync      # 建库建表 + 灌入卡片（幂等）
```

AI 精读需要模型：本机 `ollama serve` + `ollama pull qwen2.5:7b-instruct`；
没有模型就设 `AI=off`，**少了它只是少一个按钮，不是少半个应用** ——
卡片、复习、图谱、笔记、文档全部照常。

改完任何代码或数据，跑一遍校验：

```bash
node back_study/scripts/check.js                # 语法/字段/编译 + 端点 API 冒烟 + 双存储队列逐位对照
cd back_study && python -m pytest tests -q      # 白盒单测（四算法契约、FSRS 黄金值、图算法、报表、题库解析）
```

## 质量保障怎么做的

- **端到端冒烟**：`check.js` 起一个临时服务（随机端口，跑完自动关）打真实接口，
  某个参数偷偷从 400 变成 422、字段改了名，会当场报出来。
- **双存储一致性对照**：同一份到期队列分别用 `STORE=json` 和 `STORE=mysql` 各算一遍，
  逐位比顺序。排序规则在两处各有一份实现，这种不一致只有拿另一种后端比才发现得了。
- **白盒单测**：FSRS 黄金值与 py-fsrs v6.3.3 对照；PageRank 归一、Louvain 确定性、
  路径方向；错题本口径与 True Retention；Load Balance 只推迟不提前；题库三格式解析。
- **真模型 e2e**：Agent 分章、两章 grounding 打分、图注生成、图片 200/401、
  重复跑幂等 skipped、发布 2/2、删文档连图一起删。

## 已知限制（诚实版）

- **本地 7B 的精读质量明显不如云端大模型**：类比偶尔跑偏，`mechanism` 有时只是把重点换个说法。
  对质量要求高就切云端通道（`LLM_PROVIDER=cloud` + key）。
- **扫描版 PDF 没有文字层就解析不出内容**，需要 OCR；公式与复杂表格的还原度有限。
- **仿真评测的结论不等于真实效果**，见上文算法一节的局限声明。
- **JSON 文件后端在几千张卡以内够用**，再大就明显慢 —— 它每次都把全部卡读进内存，
  到这个量级请切 MySQL。
- **微信小程序还在自测阶段**，接口与分页契约已对齐，体验版分发待完成。
- **手机端的实测图是 headless Chromium 按 390×844 渲染的**，不是真机；
  滚动惯性和点击热区只有上手才知道。

## 路线图

1. 用真实复习日志替换仿真评测，把 FSRS 个性化权重从「可拟合」变成「默认启用」。
2. 卡片 Agent 的解析报告接入向量检索，让「哪一章值得出卡」有可解释的依据。
3. 学习路径从「岗位覆盖率」扩展到「先修依赖」，用图谱的层级边算真正的下一步。
4. 小程序补齐复习与问答两个页面，与网页端共用同一套进度语义。
5. 多人场景：班级与共享卡库的权限分级（现在已有注册/登录、按用户隔离的进度与管理员角色，
   缺的是跨用户的协作与授权模型）。
