用户需求澄清（两轮对话后确定）：

方案要点（已确认的设计方向）：
- 四段流水线：内容来源 → LLM 抽取成标准卡 → 单一知识库(JSON) → 双端呈现；
  自测/标记结果回流更新复习状态
- 卡片 schema 六要素：一句话本质 / 类比 / **有序机制的拆解步骤** / diagram 引用 /
  面试追问 / 复习状态。其中「有序步骤」是"""背 → 能复述"""的关键
- 动画可扩展性解法：抽象五种通用模板 + 五个渲染器
  （状态机流动、时序消息、数据管道、快照对比、树与递归），
  新知识点只填 diagram spec JSON，不手写动画
- 端上的取舍：小程序 canvas/SVG 能力弱，装不下动画。
  → Web/H5 做重体验（动画、导图漫游、导入），小程序做随身版（搜索/卡片/标记/自测）
- 关键差异功能：面试口述模式（计时 60s 对着标题说，展开对照要点）

技术选型建议：Vite + React + TS + SVG/CSS 动画（Web 端）；
Node(Fastify) 或 Python(FastAPI) + SQLite 做后端；LLM 抽取用 DeepSeek/Qwen（便宜、中文好）。

### schema 已扩增：scene 字段（真实业务场景）
用户明确要求每张卡要讲「在真实软件中怎么用」。写法规矩：
- 必须落到具体系统/具体用法/具体踩坑，禁止「在电商系统中广泛应用」这类空话
- 每条卡 2~3 条，单条 40~60 字
- check.js 已把 scene 列为必填，且要求 length >= 2

插入手法：不要手改 10 处。写一次性 node 脚本按 card id 锚定
（`id: 'xxx'` → 该卡之后第一个 `\n    keywords:` 行尾）批量插入，插完跑 check 验证。
字段在 JSON 里的物理顺序无所谓，UI 显示顺序由渲染代码决定。
