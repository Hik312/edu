## 第六轮：遗忘曲线加「掌握度趋势线」（用户要"高级"）

用户要求「遗忘曲线加曲线，高级」。已加，但**守住了一条底线**：
不是把柱状图换回曲线，而是**柱状 + 曲线双维度并存**。

### 改了什么（ProfileCenterView.vue 的 curveOption 整体分支）
- **双 Y 轴**：左轴=复习次数（`minInterval:1` 整数），右轴=掌握度（0~1，独立量程）
  - 为什么要两个轴：次数最大 5、掌握度最大 1，差 5 倍；共用一轴会把曲线压平
- **柱状保留**：三档复习次数仍是堆叠柱（离散计数不该用线）
- **新增折线**：`平均掌握度`（后端已有真实 `avgP` 字段，非编造）
  - `smooth: false` + `connectNulls: false`
  - 没复习的日子给 `null` → **曲线真的断开**
- 标题/提示同步改：「三档复习次数（左轴）+ 平均掌握度趋势（右轴）」

### ★ 核心原则（这条已写进代码注释和文档）
**图表不能画出数据里没有的东西。**
离散计数用柱状、趋势用真实数据点的折线、没数据用 null 断开——
**绝不用 smooth 插值编造中间状态**。
这与之前「遗忘曲线不是平滑衰减曲线」「面积图换成堆叠柱」是同一条原则。

### 实测验证（真实数据，admin）
日期轴从 4 天补全到 **11 天**，avgP 真实序列：
```
09-29  0.455  (有复习)
09-30  null   -> 曲线断开
10-01  0.349  (有复习)
10-02~10-07 null -> 曲线断开（6 天没学，如实显示）
10-08  0.192  (有复习)
10-09  0.117  (有复习)
```
掌握度真实下降趋势（0.455→0.117），因为 BKT 掌握度不随时间自行衰减，
只有「复习事件驱动的 p」才有值 —— 与文档里的说明一致。

## 第七轮：修曲线断线 + 补 PG 的 sessions_*（用户催办）

### ★ 我上一轮的错误（用户截图指出「曲线还是没有出现」）
设了 `connectNulls:false` 想表达「没数据就断开」，结果因为**每两个有复习的日子中间
都隔着没学的日子**，所有线段全被切断 → 图上只剩一堆孤立小圆点。
**我把两件事混为一谈**：
- `smooth:true` = 贝塞尔曲线**凭空造出**中间状态 → 真的在编数据，该禁
- `connectNulls:false` = 不连接空档 → 诚实但**过度**，导致趋势完全看不见
- 修法：`connectNulls:true` + `smooth:false` —— **用直线连接两个真实测点**
  是时间序列标准画法，不是插值编造。诚实性靠「柱状图在没复习那天是 0 高度」保留。
★ 这条教训：**区分「编数据」和「不画」是两个独立的开关，不要捆绑。**

### PG sessions_* 真修（不是降级提示）
之前只有 jsonfile 实现，PG 是空的 → 「学习时长」在 PG 配置下恒为 0h。
- `pg.py` DDL 加 `review_sessions` 表 + `ix_sessions_user_ts` 索引
  - `ts` 用 **VARCHAR(24)** 不是 TIMESTAMPTZ：前端上报 `'YYYY-MM-DD'` 或
    带时分秒两种形态，强转时间戳要么报错要么被猜成当天00:00，**制造歧义**；
    而报表只按天聚合（`report._day()`），不需要时间精度
- 实现 `sessions_append/of/count` + `sessions_clear`
  - ★ **limit 语义必须与 events_of 一致**：取「最近 N 条再正序」。
    直接 `ORDER BY ts ASC LIMIT n` 拿到的是**最旧** n 条，与 jsonfile 的
    `out[-limit:]` 相反 → 「最近学了什么」会变成「最早学的」

|卡 | 讲什么 |
|---|---|
| `algo-attn-complexity` | **O(n²) 瓶颈与解法地图**（作为这一系列的总纲卡） |
| `algo-sparse-attention` | 稀疏注意力：滑窗+全局token，O(n·w)，Longformer/BigBird |

### ★ 这批卡的组织主线（写进注释了）
标准自注意力 O(n²) 是根瓶颈，两条解法路线：
- **路线A「让注意力更快」**：稀疏（只算部分位置）/ 线性（核技巧去O(n²)）/ 低秩

- ★ **FlashAttention 属于第三条路**：不改复杂度，是精确的 IO 优化
  ——三者常被混为一谈，卡里特意区分开了

### 关键内容点
- 线性注意力为什么需要核技巧：softmax 非线性，**不能直接交换矩阵乘顺序**
- Mamba 的「选择性」：A/B/Δ 依赖当前输入 → 每个 token 不同记忆策略
- KV Cache：**不重算但仍在长**，很多「算力不够」其实是「显存不够」

## 工业级 RAG：混合检索 + RRF 融合 + cross-encoder 重排（2026-10-09 20:20-20:35）

### ★ 先说结论：性能瓶颈**不是**候选数，是**文本长度**
我一开始按「候选数越少越快」设计，实测打脸：

固定 8 对，只改每条文本长度：
| 每条字数 | 耗时 |
|---|---|
| 50 | 458ms |
| 150 | 1006ms |
| 300 | 1664ms |
| **500** | **3222ms** |

**几乎线性**。我最初设`MAX_CHARS=500`（想着模型512 token 上限），

改到 **150 字**（title + oneLine + 机制前几条）：**7735ms → 2683ms**。
★ 教训：**先量哪个维度是瓶颈再优化**，别按直觉调。

| 8 | 1138ms |
