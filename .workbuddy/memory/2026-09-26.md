## 后端：鉴权改用 PyJWT（用户要求「不要零依赖」）

`core/security.py` 原来手写 base64url + hmac-sha256，唯一理由是"零依赖版 server.py 不能装第三方包"。
用户明确说不要这条约束了（后面还要接 Redis，本来就要装依赖），已换成 PyJWT 2.15.0。

关键结论：
- **`jwt.decode()` 必须显式传 `algorithms=ALLOWED_ALGS`**（白名单只放 HS256）。
  手写版压根不看 header 的 alg，这次侥幸没出事（它无条件按 HS256 验签，alg:none 会验签失败），
  但那是运气 —— 省略 alg 校验是 JWT 的经典漏洞。**别为了"让它跑起来"改成读 header 的 alg。**
- **老 token 不受影响**：PyJWT 的 HS256 就是 HMAC-SHA256，算法和密钥都没变 → 升级后不会被强制重新登录。已测试确认。
- 密码哈希**仍用标准库 pbkdf2_hmac**（120k 轮），没换 bcrypt/argon2 —— 换它要引 C 扩展依赖，
  且 120k 轮对这个规模够用。真要加固优先调 `PBKDF2_ROUNDS`。
- PyJWT 已加进 `requirements.txt` 的**必需**段（不再是可选）。

新增 `back_study/scripts/test_security.py` —— 项目第一份自动化测试，16 项断言：
签发/验签、老 token 兼容、无效输入一律 None、**alg=none 与 alg=RS256 伪造被拒**、口令哈希边界。
跑法：`back_study/.venv/Scripts/python.exe back_study/scripts/test_security.py`（不用起服务、不碰库）。
**换 JWT 库 / 调 PBKDF2_ROUNDS / 改密钥来源之后先跑它。**

### ★ pyflakes 的假阳性（本轮最值钱的教训）
`app/config.py` 的 `from . import DATA_DIR, WEB_DIR` 是**故意的再导出**（`main.py` 从 config 取 `DATA_DIR`），
pyflakes 报 "imported but unused" → 照删后 **`py_compile` 全绿、`check.js` 语法检查也过，
直到真正起服务才炸 ImportError**。
**根治**：不要靠转引 —— `main.py` 改从 `app/__init__` 直接取，消掉这层。
**规则：静态分析报的"没人用"必须 grep 跨模块用法再动手。**
pyflakes 已接进 `check.js` 作为**建议性**步骤（只提示不判失败，因为它会把再导出误报成死代码）。
清出的 4 个真未用 import 里，`importer.py` 的 `urllib.request` 正是当年 `parse_llm` 自己拼 HTTP 留下的残骸。
