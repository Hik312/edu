## MCP 再加 code-exec 工具（完善）

按之前排序，加了教学价值最高的**代码执行沙箱**。`run_python` 让 QA Agent 能跑代码验证答案/演示算法，从"只检索"升级成"会动手验证"。

⚠️ 关键坑（复盘必记）：**stdio MCP server 里再 spawn 子进程，必须显式重定向三路 stdio**。第一版用 `capture_output=True`（只重定向 stdout/stderr，`stdin` 仍继承），结果 `run_python` 一定超时——因为子进程继承了 MCP 的 JSON-RPC **stdin 读端**，在 Windows 下挂起。隔离跑（stdin 是普通管道）完全正常，塞进 stdio 服务才挂，定位花了这一步。修复：`stdin=subprocess.DEVNULL` + stdout/stderr=PIPE + `close_fds=True` + Win 加 `CREATE_NO_WINDOW`。

实测（venv 3.10.11）：`build_tools()` 现返 6 工具；`run_python` 正常代码秒回、超时(2s 跑死循环)→"执行超时"、空代码→"没有收到"、报错→带 traceback 回传，全过。注意项目 venv 没装 numpy，`import numpy` 会 ModuleNotFoundError——正常报错透传，往 venv `pip install` 即可用。

## react 问答内置「卡片校验 / 自纠」（把校验挂进问答流水线，不是独立功能）

**先记一个走错的路**（下次别重犯）：我第一版把校验做成了独立的「校验/自纠」面板按钮，
用户明确否定——他要的是**校验嵌进 Agent 流式问答(react)这条流水线**：RAG检索→联网MCP→验证检索到的卡
→回答→(若有错)反问用户是否改→允许则直接改卡。独立面板是错的。**需求先复述确认再动手。**

最终设计（用户确认：校验引用到的前 2-3 张、每次 react 自动跑）：
- `agent/verify/runtime.py`：`verify_cards(cards)` 逐张联网取证 + **一次批量 LLM 判别所有卡**，
  只返回 `proposed_patch` 非空的（真要改的）；`_judge_batch` + `BATCH_VERIFY_SYS`。
- 落库：先出 `proposed_patch` **绝不自动改**；用户点「确认修正」才调
  `POST /api/agent/verify/apply`→`db.apply_card_patch`；`/verify/revert` 可还原。
- `_sse`(app/routers/web/agent.py)：**先发 `done` 帧**（前端立刻解除「生成中」），
  **再**跑慢的校验，结果作 `event: verify` 帧补发。校验失败全吞，不影响已给出的答案。
- 前端：askStream 解析 `event: verify`→onVerify→挂到该条消息 `m.verify`；
  AskView 气泡内渲染「校验发现可疑 + 字段diff + 确认修正/忽略/还原」。
  chat store 的 `pushAssistant` 加 `verify:null`。

★ 两个实测坑：
1. **批量 vs 逐张**：逐张判别每张卡喂一遍「整卡+联网」给模型（每张 20~60s，3 张近 **5 分钟**，

## 复习队列「刷新后进度丢失」——根因是纯前端态没持久化

## 复习进度按「方向」隔离（切换方向从头开始 / 方向没变接着剩余量）

- 顺序无关用sorted（用户点方向 chips 的顺序不该影响签名）。

## 修三个前端问题：深底深字 / 死转圈 / 段落空隙

用户截图三个症状，逐个定位到不同层，**都不是表面样式问题**：

### 1. 用户气泡深底深字（真 bug，根因在共享组件）
`MarkdownRenderer.vue:116` 写死了 `color: var(--tx)`（墨褐深色）。用户和助手
**都走这个组件**，scoped 选择器优先级又高于父级气泡 → 用户气泡里浅色字被
刷成深褐色，深底深字整块看不清。父级怎么设 color 都没用。
修法：`.md-container` 改 `color: inherit`，并把 `:deep(h1~h4)` / `strong` /
`blockquote` 里写死的 `var(--tx)` / `var(--mu)` 全改 `inherit`。
★ 教训：**共享渲染组件不要写死文字色** —— 它被用在深浅两种底色上，
任何一处 var(--tx) 都会在深底上炸。

### 2. 用户气泡配色改淡（截图看实心深靛蓝"像贴片"）
实心深色块压牛皮纸上很跳，跟整页纸质打架。改成
`color-mix(var(--ac) 9~14%, var(--panel))` 的淡靛蓝底 + `--ac-dim` 深靛蓝字
+靛蓝细边。同一色相族，仍分得清谁说的话，但属于这张纸。

### 3. 回答空隙太大（**根因不是margin，是 white-space:pre-wrap**）
★ 排查走了弯路：先以为是 MarkdownRenderer 的 `p{margin:10px}`，改成 6px
**完全无效**。真凶是 `.bubble { white-space: pre-wrap }` ——
正文由MarkdownRenderer 渲染成 `<p>/<ul>/<li>`，pre-wrap 让 HTML 源码里的
换行和缩进**全部变成真实空白行**，每个 `<p>` 上叠三四行空白。
修法：`.body { white-space: normal }`（Markdown 自带块级间距，不需要保源码换行），
只给 `.row.user .body` 保留 pre-wrap（用户提问是纯文本，换行是有意的）。
★ 教训：Markdown 渲染区**绝不能开 pre-wrap**；纯文本提示（err/typing）才开。

### 4. 步骤条「答完还在转圈」（后端漏收尾帧）
`{done:true}` 收尾帧**只有校验那步有**，「组织回答…」永远没人收。
表现：答案全文显示了，步骤条还在转，且那个圈永不消失。
修法：`_sse` 在 `done` 帧后补一帧收尾；**`except` 分支也补**（否则出错时也留圈）。
帧协议文档同步写明「每个新增 step 必须有一次收尾帧」。
实测帧序（打桩校验）：
`step(检索)→step(组织)→正文→sources→done→step(收尾组织)→step(校验)→verify→step(收尾校验)`
3 新增 + 2 收尾（最后一步的收尾在 finally 里）。

★ 测试教训：`_sse(rt, question, ...)` 的**第一个参数是 rt**，我两次传错导致
误判成代码有错；打桩要`agt.rt = FakeRT()` 或按位置传参。

## 回答加段首缩进（中文排版）

用户要「每段有首字符空格，不然怪」。`.body :deep(p)` 加 `text-indent: 2em`。
- **必须用 text-indent 而不是 padding/margin-left**：只缩进第一行，第二行顶格
  才是中文段首缩进的正确形态；padding 会把整块推走。
- **三处要排除**，否则双重缩进更难看：`:deep(li p)`（li 自带项目符号+左缩进）、
  `:deep(blockquote p)`（缩进本身是「引别人的话」的语义标记）、代码块是 pre 不受影响。
- 用户气泡不缩进（`.row.user .body :deep(p){text-indent:0}`）——他写的是一句话，
  不是段落，缩进反而怪。

## Redis 业务缓存落地（第1、2 个落点）

现状核对：`core/cache.py` **只有 get/set/delete/clear/ping，没有 incr / setnx**
→ 所以「分布式锁/计数器」类需求暂时做不了（要先扩接口）。
Redis 原本**只在算法层**用（BKT参数 ttl1h / 掌握度 ttl10min），业务层一处没有。

### ① 卡片校验结果缓存 `agent/verify/cache.py`（收益最直接）
校验一张卡 60s（联网+模型），结论对同一份内容是稳定的。
- key = `study:verify:<cardId>:<内容指纹>`，**靠指纹失效不靠 TTL**。
  刻意不用「id+时间」：改了卡在TTL 到期前会一直返回旧结论，
  而"卡已改却给旧校验建议"比慢严重得多。
- 指纹字段必须与 `_SHOW_FIELDS` 一致（漏一个→改了那个字段却命中旧结论）。
- ★ **「没发现错误」这个结论也必须缓存** —— 不缓存它等于每次重跑最贵的流程。
- 实测：首问 60s → 命中 web=0/judge=0；改一张卡 → web=1/judge=1（只重算那一张）。

### ② 问答答案缓存 `agent/qa/ans_cache.py`（风险高，所以失效更严）
flow 实测 40~103s，同问题重复问不该重跑。
- key = md5(问题 + 模式 + 联网开关 + **卡片内容指纹**)。
- 三条保守约束（都实测过）：
  1. **有 history 一律不查缓存**（历史不同答案就不同，命中会答偏）；
  2. **只在「检索没命中任何卡」时才写缓存** —— answer 节点不写 state，
     拿不到"用了哪几张卡"就构造不出正确失效指纹 → 宁可不缓存；
  3. 超长答案(>8000字)跳过。
- 命中时**按 24 字分块吐字**（实测340 字→14 块），保持流式观感，
  否则前端会突然整段出现。
- 环境变量开关：`VERIFY_CACHE=0` / `QA_CACHE=0` 全局关。

### ③ 步骤条「答完还在转圈」改成「后台核对」
根因不是漏改：react 下 **sources 在 done 前发，但校验在 done 后才开始转**，
所以"引用卡片出来了"= 答完了，此时那个圈转的是**后台增强任务**。
改法：step 帧加 `kind:'bg'` → 前端不进步骤条，改渲染成一行**呼吸点**
（不用转圈，转圈会让人以为"还没答完"），并在无建议时也发收尾帧。
前端的空气泡坑：`m.steps` 空数组时 v-if 为真但 v-for 什么都没有 →
必须加「一个步骤帧都没到」的兜底行，否则出现**空白胶囊**（用户实测截图）。

### ④ flow 模式改成真流式
原来 flow 走 `stream:false` 一次性等全文（空白 20~40s）。
`nodes.answer` 加 token sink（ContextVar 传递，因为 LangGraph 节点只收 state），
`runtime.stream_flow` + SSE 层用「后台线程生成 + 队列转发」。
实测：444 帧正文 / 出字跨度 103.67s（首帧 0.1s）。
★ 流式不改质检：grade 拿到的仍是完整答案，用户可能看到答案被覆盖重写。

★ `core/db.py` 的 `storage_info()` 加了 `cache.biz.{qa,verify}`——
降级必须可见是项目铁律，业务缓存能被关掉，必须报出来。

## Redis 第三落点：检索缓存（含一个"静默失败"的坑）

**先实测再决定做不做**——这一步推翻了我自己的假设：
- `due_list` **只要 67ms**（已有 SQL 快路径 LEFT JOIN+索引）→ 不值得缓存
- `mastery_map` 67ms，其中 **all_cards() 占 59ms**
- ★ **`retrieval.retrieve()` 384ms 才是真瓶颈** → 缓存它，实测 **384→63ms，6.1x**

### 检索缓存 `agent/qa/retr_cache.py`
- key = md5(查询 + k + **全库检索指纹**)；缓存内容**只有 id + score**，
  **card 本体每次现取** —— 所以改卡立刻生效，缓存不会变成"内容陈旧"的来源。
- 全库指纹只含**影响检索**的字段(title/oneLine/keywords/tags/mechanism/
  analogy/subject)；**level/nextAt 不进** —— 标了卡不该让全库检索缓存作废。
- 指纹本身有 30s 短缓存：算一次指纹要读一遍全库(59ms)，每次检索都重算
  就把省下的时间还回去了。用 TTL 换计算（改卡最多 30s 后反映到检索缓存）。

### ★★ 踩坑：SearchHit 没有 .get()，静默失败
`SearchHit.__slots__ = ('id','card','score')` —— **不是 dict，没有 .get()**。
我写 `put` 时用 `h.get('id')` → AttributeError → 被 `except: pass` 吞掉
→ **缓存从来没写进去，却完全静默**，表现是"加了缓存但一点没变快"（实测 0.9x）。
- 教训：**写缓存/读缓存的代码不要裸`except: pass`**，
  至少 `print(..., file=sys.stderr)`。否则你永远查不出"缓存没生效"。
- 同一类坑：`ans_cache.card_fingerprint` 原来在循环里对每个 id 调
  `db.all_cards()`（N 张卡 = N×59ms）→ 改成**一次全量取再查表**，
  3 张卡从 177ms 降到 59.7ms。

### 测试方法教训
写缓存的测试**不要硬编码 TOP_K**：`C.TOP_K=3`（环境变量 `AGENT_TOP_K`），
我传 5 导致"缓存前后命中不一致"的假警报。要从 `config` 读真实值。

★ 健康检查 `storage_info()` 现在报三个：`cache.biz.{qa,retr,verify}`，
各自带 enabled/backend/degraded/ttl —— 降级必须可见是项目铁律。

### 我上一轮写错了什么（对照规范的自查）
1. **写成"我做了什么"的流水账** —— 标题都是"（2026-10-08 新增）"、
   正文写"我原以为 X"。规范要求写**为什么这么设计**，不写什么时候做的。
2. **缺"系统不做什么"** —— architecture-doc 模板明确要写
   "What does this product NOT do"。开头只有"能做什么"。
3. **ASCII 大图** —— 改Mermaid。ASCII 改一处要手工重排全图，且 GitHub
   不渲染、字体对不齐。
4. **数字过时没实测** —— 写"69 文件/11.2k 行、端点 50 个"，
   实测是 96/20.0k、端点 77。`core/db.py` 也从 1805 → 1917。
5. **缺"按目的选读法"** —— 开发者文档开头没告诉读者该读哪几节。

### Mermaid 布局踩坑（实测三次才对）
- **subgraph 嵌套 + direction 不生效**：3 层 subgraph + `direction LR`
  结果布局全乱、箭头 crisscross。
- **根因**：`CORE` 有 4 条出边指向不同 subgraph，Mermaid 会把它们横向铺开。
- **解法：减少节点与边**。把 store/algostore/Redis **合并成一个节点**，
  边从 9 条减到 7 条 → **零交叉箭头**，四层清晰。
- ★ 验证方式：写个临时 HTML 引 `cdn.jsdelivr.net/npm/mermaid@11` 渲染截图，
  别靠肉眼猜语法对不对（`subgraph`/`end` 配对 + 引号配对可先静态查）。
- ⚠️ `<br/>` 在该渲染器里**被吞**，文字会连在一起。

### 文档三种文体的分工（Diataxis，改造后）
| 文档 | 文体 | 读者 |
|---|---|---|
