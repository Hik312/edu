# 算法层 `back_study/algo/`

间隔重复 / 知识追踪算法都放这儿。要用就 `import algo`。

**依赖方向是单向的**：`core/db.py` 用 `algo`，`algo` **不**反向依赖 core。
所以这个包拿一个 dict 就能跑 —— 不起服务、不连数据库、不读文件，
调参和单测都在秒级完成。

## 文件

| 文件 | 职责 | 改什么的时候看它 |
|---|---|---|
| `base.py` | 契约 `Algo`、评级常量、日期工具、防御式取值 | 加字段、改契约 |
| `sm2.py` | SM-2 简化版（**当前默认**，系统一直在跑的那个） | 调难度因子上下界 |
| `fsrs.py` | FSRS-4.5 记忆稳定性模型 | 调目标保持率、权重 |
| `bkt.py` | BKT 贝叶斯知识追踪 + **四参数拟合** | 调网格、拟合门槛、`interval_of()` |
| `__init__.py` | 注册表：`get()` / `names()` / `register()` | 加新算法 |
| `demo.py` | 对拍台 CLI：同序列喂两个算法，比复习次数 | 评估要不要换算法 |

## 怎么用

```python
import algo

algo.get().schedule(prev, level)          # 用默认算法
algo.get('fsrs').schedule(prev, level)    # 临时指定
algo.names()                              # ['fsrs', 'sm2']
```

命令行对拍：

```bash
python back_study/algo/demo.py --list
python back_study/algo/demo.py                        # 默认序列，365 天
python back_study/algo/demo.py --seq 3,3,2,1,3 --days 180
python back_study/algo/demo.py --algo fsrs --retention 0.85
```

## 换算法

优先级和 `STORE` 一样，不用改代码：

1. 环境变量 `ALGO=fsrs`
2. `back_study/config.local.json` 里 `"ALGO": "fsrs"`
3. 都没有 → `sm2`

**算法名写错会直接抛 ValueError，不会悄悄退回 sm2。** 配置拼错却假装成功，
比启动失败糟糕得多 —— 你以为在评估 FSRS，其实跑了三个月 SM-2。

## 加一个新算法

1. 写 `algo/xxx.py`，继承 `Algo`，实现 `schedule(prev, level, today=None)`
2. 在 `algo/__init__.py` 里 `register(Xxx())`（传**实例**不是类，实例才能带参数）
3. 登记进 `scripts/check.js` 的 `pyFiles` 清单（手维护的，漏了就不会被编译检查）

返回值只能是这 6 个键：`level / interval / ef / reps / nextAt / updatedAt`。
**多加一个键都会被 MySQL 静默丢掉** —— `progress` 表就是这 6 列，
JSON 后端看着好好的、切到 MySQL 行为就变了。要加字段先改存储层三处：
`mysql.py` 的 `DDL_TABLES` + `schema.sql` + `_build()` 的必需表探测。

## 实测对比（2026-09-29）

同一串评级 `会会会·模糊·会会·不会·会会会`，模拟 365 天：

| 算法 | 复习次数 | 末次间隔 | 特点 |
|---|---|---|---|
| SM-2 | 15 次 | 176 天 | 间隔按 ef 硬乘，1→3→8→26…，指数增长 |
| FSRS | 6 次 | 427 天 | 按记忆稳定性反解间隔，增长随复习次数自然放缓 |

**复习次数少 ≠ 更好。** FSRS 排得少是因为它**认为**你记得住；真正的判据是
实际回忆成功率，那需要事件流 —— 现在还没有，所以 FSRS 目前只能当对照，
别急着切过去。

## 两个坑

1. **`ef` 字段是通用数值槽**：SM-2 用它存难度因子（1.3–2.6），FSRS 用它存
   难度 D（1–10）。从 SM-2 切到 FSRS 时旧的 ef 会被当成 D 读，复习几次就回归正常。
2. **老 bug（搬包时顺手修的）**：原实现判断 `isinstance(ef, (int, float))`，
   而 MySQL 的 `ef` 是 DECIMAL、pymysql 取回来是 `Decimal` → 每次复习都被
   静默重置成 2.5，**等于用了数据库之后难度因子永远失效**。回归脚本实测
   99% 的组算错（该 62 天算成 82 天）。现在统一走 `base._num()`。

## BKT：回答的是另一个问题

**SM-2 / FSRS 和 BKT 不是替换关系，是叠着用的**：

| | 回答什么 | 输出 |
|---|---|---|
| SM-2 / FSRS | 下次**什么时候**看 | 一个间隔（天） |
| BKT | **到底掌握没有** | 一个概率 p ∈ [0,1] |

正确用法是 BKT 定优先级（先学没掌握的）、SM-2 定时间（掌握的少看）。
这里为了塞进统一的 `schedule()`，让 BKT 也输出间隔 —— 用 p 去驱动：
`interval = 1 + 20·p²`（p=0 → 1 天，p=0.5 → 6 天，p=0.9 → 17 天）。

### 四参数（都能用人话解释）

| 参数 | 含义 | 典型 |
|---|---|---|
| `p_init` | 没学过之前的先验掌握度 | 0.1–0.3 |
| `p_transit` | 练一次从不会变会的概率 | 0.05–0.2 |
| `p_slip` | 会但答错（手滑） | 0.05–0.2 |
| `p_guess` | 不会但蒙对 | 0.1–0.3 |

```python
import algo
p = algo.bkt.step(0.3, correct=1, algo.BKT_DEFAULT_PARAMS)
params, info = algo.bkt_fit([[1,0,1,1], [0,1,1]])   # 从自己的数据里拟合
```

### 拟合才是重点

公式就四行，抄谁的都一样。**值钱的是用你自己的答题记录把这四个数拟合出来**
——「我在自己学生的真实数据上拟合出 slip=0.07」这才叫自己的算法。

`fit()` 用网格搜索（625 组合，不到一秒），不会掉进局部最优，也不用引 numpy。
数据不够时**拒绝拟合、返回默认参数**并说明原因：20 条记录拟合 4 个参数必然
过拟合，那时候默认参数反而预测得更准。

门槛：至少 **8 个知识点 / 30 条记录**。

### 实测（2026-09-29）

用已知参数（transit=0.15, slip=0.10, guess=0.25）造 168 条记录再拟合：
拟合结果的似然 **-78.71 优于真值参数的 -79.56**（拟合确实找到了更好的解），
三个参数的量级都对。108 条的小样本上偏差会变大（transit 0.15→0.30），
这是数据量的问题，不是实现的问题 —— 攒到几百条再看。

### BKT 特有的两个坑

1. **`ef` 在这里是掌握度（0~1）**，而 SM-2 的 ef 是难度因子（1.3–2.6）。
   从 SM-2 切过来时旧值会被读成 p=2.5 —— 代码里夹回 [0,1] 了，
   但看 `progress.json` 的人要知道 2.5 和 0.83 不是一回事。
2. **一直答错也不会降到 0**。每次练习都有 `p_transit` 的概率让人学会，
   所以掌握度的下界是 transit。这是模型本意，不是 bug ——
   第一版测试断言"连错 30 次 → p≈0"，实测 0.114 直接 FAIL。
