## 知识图谱（现行：ECharts）

实现在 `web/src/views/graph/GraphView.vue`，渲染封装在 `web/src/components/EChart.vue`。

**为什么不用自绘 Canvas**：旧版（单文件页）是自己实现的力导向 + 粒子场，效果确实炫，
但三个问题绕不过去 —— ① 没有 tooltip / 缩放 / 图例筛选，要就自己写一套，写完还想加拖拽又是一套；
② 节点多了就掉帧（canvas 每帧重画全部节点，几百个点必卡）；
③ 网页端和小程序要维护两份几乎一样的物理参数。
ECharts 的 force 布局用四叉树做斥力近似，几十到几百个节点都稳，缩放、tooltip、图例筛选全是免费的。

**三个不能改回去的实现点**：

1. **斥力不能写死常数。** 现在是 `repulsion: max(120, 4200 / max(n/12, 1))` —— 固定值在小图上
   会把点甩到天边，在大图上又全糊在中间。这条是旧版踩出来的（写死 `REP = 9000/24000` 时，
   手机画布 343×430 上实测中心区域节点占比 0.00、贴边节点 0.94、最近两节点净间距 **-9.7px**，
   即全挤在四条边上还互相重叠；改成随尺度算出来的理想边长之后是 0.37 / 0.00 / +14.7px）。
   同一个道理在旧版里还有两条配套规则，换库之后由 ECharts 承担：引力和斥力必须同阶
   （斥力 `k²/d²`、引力 `d²/k`，用 `k²/d` 时斥力量级远大于中心回拉，节点会被顶到四边）、
   收尾不能硬夹边（夹边是「空心方框」的直接原因）。
2. **节点大小按 PageRank，不按 degree。** `degree` 数的是「我连着几个知识点」，
   PageRank 数的是「连着我的知识点有多重要」：AQS 详解 degree 11（全库最高）只排 PR 第 40，
   一次阻塞 `read()` degree 9 却是 PR 第 1 —— AQS 挂了一堆 relate 是造卡时手勤，
   被一堆 JVM 卡指着才是真的中心。排名来自 `/api/graph/rank`，悬停时两个数和各自排名都给出来。
3. **懒初始化：容器拿到非零宽高之后才建实例。** 骨架态用 `v-show`（元素存在但 `display:none`），
   实测宽高 0×0，ECharts 会把 0×0 记成画布尺寸，力导向在这个尺寸下把几十个节点全收敛到原点；
   骨架一撤、ResizeObserver 补 resize，**坐标系回来了但已收敛的布局不会重算** ——
   表现是「画布一片空白，只有几个标签飘在边上」。柱状/饼图这类静态布局会在 resize 后重算占比，
   所以只有图谱中招，一开始被误判成「force 的 repulsion/edgeLength 参数不对」，白调了半天。

**分组与配色**：社区配色来自后端 `/api/graph/insight` 的 Louvain 社区发现。
手选分类是按**造卡时分的类**，Louvain 是按**实际连边密度**分的，两者经常对不上
（实测：MySQL 索引那 4 张卡自成一社区，手点 chips 是选不出来）。
结构节点按它**所在社区里最多的那张卡**上色 —— 一个 topic 底下全是 Java 卡就该是 Java 那支颜色。
刻意不用 ECharts 的 legend：graph 系列的图例筛选要求每个节点带 `category` **索引**，
而这里的分类是 type 字符串，为图例再维护一份「type → 索引」映射等于把分组逻辑复制一遍。

**模块筛选**：全量图（四百多张卡 + 结构节点）力导向会糊成毛线球，所以顶栏两级 chips（分类 → 科目），
选中哪个就只画哪个的子图；跨模块的 related 边由后端按 id 白名单丢掉，这正是"其他模块不出现"的语义。
结构节点按选中范围在前端裁剪（选了分类就去掉 category，选了科目就保留 subject 当根）——
裁剪是**视图**的事，换种选法要换套规则，所以不给后端加参数。

**验证「真的在动」**：截图工具只能拿到某一帧，所以判断动画有没有在跑，靠截
`--virtual-time-budget=7000` 和 `=11000` 两张图做像素 diff —— 实测 32.9% 的像素发生变化
（4.07% 为强变化），说明收敛之后画面仍在持续演进。旧版单文件页还留过一个 `?debug=1`，
把帧数 / FPS / 模块质心写进标签标题，方便无头环境读数；Vue 版改掉了这个入口，
要读数就开浏览器 devtools 看 ECharts 实例，别在页面里留调试开关。

## 移动端：几个不能改回去的写法

- **底部标签栏用 flex 布局的固定项，不用 `position:fixed`。** fixed 是相对视口底部定位的，
  微信内置浏览器的工具栏正好盖在上面 —— 之前就是这么整条看不见的。
- **整屏高度用 `--vh`（JS 写 `window.innerHeight`），不用 `100vh`。** 移动浏览器的 100vh 是
  "最大视口高度"，含被地址栏/工具栏遮住的部分，拿它当整屏高会把底栏顶到可视区外面。
- **列表项是圆角卡片**（`#cards` 有内边距、`.item` 是卡片），不是贴边的横线。
- **分类栏是两行横向滚动**，不是竖着堆三条。
- **笔记是"列表 → 编辑"两屏**（`body.note-focus` 控制），不做左右分栏；编辑页顶部有返回键。
- **要滚动的面板必须显式给高度**（`flex:1` + `min-height:0`），不给高度布局会塌。
  图谱面板因此是「工具条 / 画布（flex:1）/ 图例」三段式。

## 视觉层（外观）

配色令牌集中在 `web/src/styles/tokens.css`，`:root` 里那几个变量是唯一出处
（`--ac` 主色、`--bg` 最底色），别在规则里散写 hex；图表配色另有唯一出处
`web/src/config/theme.js`。极光背景 + 玻璃拟态 + 微动效这几条纪律：

- `.aurora` 用 `mask-image` 径向淡出，因为正文区在画面中央，极光糊在那儿会把字压得发虚
  （笔记页最初就是一片褐色脏污）。
- 顶栏 / 底栏 `backdrop-filter: blur()` 做毛玻璃；内容面板补一层薄底，
  极光只作氛围若隐若现，不牺牲阅读对比度。
- 覆盖规则要写在 `@media (max-width:820px)` **之前**，写在后面会把手机端的覆盖压掉。
- 全站只有一套主题变量，不要同时写 `data-theme` 和 `class="dark"` —— 混用会导致
  Element Plus 的暗色变量立刻生效、暗色页面上一半文字是黑的。

## 精读链路的两个刻意设计决定

1. **前端逐章调用，不用批量接口。** 批量（`batch` 参数）一次送 4 章是快 3 倍，
   但章节又短又相邻时，7B 模型会把 A 章的内容安到 B 章头上（实测串味，且随机复现）。
   单章调用永远不串，还能显示 `3/10` 的进度。后端保留了批量能力，
   并且带**对齐质检**：用返回值与原文的字符二元组重合度打分，
   对不上、或类比写成说明书的，自动退回单章重跑。

2. **单次抽取不引 LangChain / LangGraph。** 这里要的只是「一次结构化抽取 + 解析失败重试
   + 类比不合格重问」，三个函数就写完了（`llm.enrich()` 内部一个带条件的重试）。
   引框架会给零依赖后端塞进几十 MB 依赖，而收益是负的 ——
   单次 LLM 调用不需要编排，编排的价值在「多步、有分支、要维护状态」的场景。
   真正的多步编排在 `agent/`（LangGraph，可选依赖），精读这条链至今只用标准库 `urllib`。

**推理模型必须关掉思考链**（代码里传 `think: false`），否则 token 全烧在思考段、正文是空的 ——
`deepseek-r1` 这类模型实测过，有降级重试兜底。

**卡片 Agent 的关卡设计**：分章由 LLM 主导但规则先切一版当候选（按层级折叠，子标题整块折进父章、
空壳章丢弃，一章内容完整）；合并回正文时扁平下标必须严格等于 `range(n)`，对不上就原样返回 ——
精修只可能变好。出卡前先停在解析报告上等人勾选（目录、封面、参考文献这类没用的章先剔掉），
生成后自检（对齐分 ≥ 阈值、keywords 必须出自原文）不过也落草稿，但标「需人工把关」；
发布仍然走 `/api/drafts/publish` 那套字段检查 —— 半自动的脏数据进不了卡库。

## 「两个后端」这段历史的教训

零依赖版（纯标准库的 `server.py`）存在过两年多，2026-09-26 移除。
它换来的是**每个接口写两遍 + 冒烟跑两遍**，代价是真金白银。
而它作为"对照"的价值其实有反向的一面 —— 移除时才暴露：

> `check.js` 的存储一致性对照一直用 `?limit=1000`，而 FastAPI 版的上限是 **500**
> （`learning.py` 的 `Query(50, ge=1, le=500)`），请求直接 400。
> 零依赖版不校验这个上限、照常返回，于是那份对照**一直是拿空队列比空队列**，
> 还打印一句 SKIP 假装没事。

**宽松的那套实现会帮严格的那套把错误吞掉。** 两套实现互为对照有个前提：
不一致要能被看见，而不是被其中一套的宽容吸收掉。
现在这条教训落在三处：缺 fastapi/uvicorn/PyJWT 的解释器**直接判失败**而不是静默跳过
（跳过就是假绿）；降级到 JSON 存储时必须在启动横幅和 `/api/storage` 里留下可见的告警；
以及内置卡内容指纹对不上时报 `stale` 并回落到文件，绝不端出「源码已改、库里还旧」的版本。

## 局域网地址探测（`core/netinfo.py`）的两次翻车

1. 不能用 `socket.gethostbyname(hostname)` —— 装了 VirtualBox / Hyper-V 的机器上它会返回
   Host-Only 网卡地址（本机实测 `192.168.56.1`，手机连它必然超时）。
2. 也**不能只靠 UDP 出口 IP**。改用出口优先后确实好过一阵，直到这台机器上开了 TUN 模式的
   代理软件：默认路由被虚拟网卡劫持，出口 IP 变成 `198.18.0.1`（代理的 fake-ip 段）——
   按出口 IP 排最前，恰好把最不可能连上的那个排到了第一位。

现在的规则是打分排序：真实内网段（10/8、192.168/16、172.16/12）加分，
代理 fake-ip / Host-Only / link-local / CGNAT / Docker 网桥重扣分，出口 IP 只小幅加分。
实测真实地址稳定排第一，虚拟网卡沉底但**不删除** —— 万一你确实要在虚拟网络里访问。

## 存储层：为什么只有一处查询值得上数据库

**今日到期队列**。文件后端要把全部卡读进内存、逐张比对进度、再 Python 排序；
到了库里是一条 `LEFT JOIN + ORDER BY`，`next_at` 上有索引，卡从 20 张涨到 2 万张是同一个写法。
排序规则（不会 → 模糊 → 未标记 → 会，同档逾期久的优先）在两套实现里各有一份，
所以 `check.js` 里专门有一段**把同一个服务起两遍（一遍 `STORE=json`、一遍 `STORE=mysql`），
拿两条队列逐位比** —— 这种不一致只有用另一种后端时才发现得了。

表结构取舍：

| 表 | 存什么 | 为什么这么存 |
|---|---|---|
| `cards` | 内置卡 + 自定义卡，`origin` 区分 | 只把要按列查的字段（category / subject / domain / title）提成独立列，`mechanism`/`diagram`/`related` 这些**永远整张一起读写**的留在 `payload JSON` 里。拆成子表只会让每次读卡多 5 次 JOIN |
| `progress` | 复习进度 | 反过来**全部拆成标量列**并给 `next_at` 建索引 —— 到期队列就该是一条 SQL |
| `notes` | 笔记 / 卡片下的「我的理解」 | 有 `card_id` 的就是后者 |
| `documents` | 整份导入的资料 | `chapters` 一个 JSON 列。一份八股文几十章，拆表后「打开文档」要先 JOIN 再拼回来，白折腾 |
| `drafts` | 待入库的草稿 | 缓冲区，不是卡 |
| `meta` | 键值杂项 | 放内置卡的内容指纹 |

`cards` 上还有一条 **ngram 分词的中文全文索引**（`ft_cards`），MySQL 内置 ngram 插件，不用装额外组件。
目前搜索仍然走 Python 的字段匹配 —— 理由很直接：两个后端的搜索结果必须一字不差，
而在几百张卡的规模上，SQL 全文检索换来的那点性能远不够抵「两套搜索语义不一致」的风险。
索引建着不碍事，卡量上来（几千张）之后再切换实现，届时以全文检索为准。

## 后端实现的三条约定

- **端点写同步 `def` 而不是 `async def`。** db 层是同步文件 IO，在 `async def` 里直接跑会卡住
  事件循环（整个服务一起等，一个精读请求能堵死所有人）；FastAPI 见到 `def` 会自动丢进线程池。
- **`/api/llm/status` 返回 `ok:false` 时 HTTP 仍是 200。** AI 不可用是正常状态不是故障，
  前端据此渲染提示而不是弹错误。
- **参数错误的状态码要能指认字段。** 请求体超限返 `413`（`app/config.py` 的 `MAX_BODY`，
  错误话术里写着当前上限），查询参数写错返 `400` 并指出参数名（Pydantic 兜的）。
  这条纪律的来源见上面「两个后端」那段 —— 400 和 401 混用会让「密码错」在登录页上
  表现成「刷新一下提示登录已过期」，人会觉得页面坏了。

## 冒烟测试的账号口令从哪儿来

`check.js` 与 `smoke_paper.py` 共用一组冒烟账号，口令**不进仓库**：
环境变量 `EDUPATH_PROBE_PASS` 优先，其次读 `back_study/.probe.json`（已 gitignore），
两份都没有时随机生成一个写进去。第一次运行用它注册，之后只能拿同一份口令登录，
所以必须持久化而不是每次随机；删掉 `.probe.json` 等于换口令，
要先把本地库里的 `zz_check_probe` 删掉才能重新注册。

以前这里写死了一组口令，而 `web/public/_seed.html`（登录种子页）也内置了同一组默认值 ——
`vite build` 会把 `public/` 原样拷进 `dist/` 并随前端发布到公网，
等于同时把口令放进仓库和线上。现在 `_seed.html` 只接受 `?user=&pass=` 传参，
没有参数就回登录页；`smoke_paper.py` 生成的 `dist/_seed.html` 写的是 token，不是口令。

**为什么必须每次重新生成种子页**：`dist/` 是 vite 的构建产物目录，`vite build` 会把它整个清空。
手工放进去的种子页活不过一次构建 —— 表现为"上一轮还能截图，重新构建之后所有需要登录的页面
都打不开"，最容易被误判成路由写坏了。headless chrome 没有"执行页面脚本之前先往 localStorage
里塞东西"的命令行能力（`--user-data-dir` 只带 cookie/profile），所以借一个真实页面来写：
它把 token 写进 localStorage 后立刻 `location.replace` 到目标页。

**截图环境的一个假信号**：`--force-prefers-reduced-motion` 不能省。
站内入场动画是 `.rise { animation: rise .44s ... both }`，`both` 意味着动画开始前元素就停在
`opacity:0`，而 headless 的 virtual-time 只快进计时器、不推进 CSS 动画的合成帧，
于是截图永远停在起始态 —— 侧栏菜单整片消失、卡片区只剩半透明白块，看起来像"页面坏了"。
