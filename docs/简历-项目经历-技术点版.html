项目描述
面向计算机与考研知识点的多 Agent 自适应学习平台。市面上的刷题App 都假设你知道自己要学什么，于是只能按固定顺序推送；而真实情况是多数人 连「从哪开始、卡住了该往哪走」都判断不了，卡在一道题上常常是因为它的 三个前置知识点里有一个没懂。 平台的做法是先把知识点之间的先修依赖显式建成图，再由三个 Agent 分工： 造卡 Agent 把教材和文档转成结构化卡片、问答 Agent 负责答疑与讲解、 规划 Agent 根据你的掌握度决定下一步学什么。掌握度不是自己填的等级， 而是由复习行为经贝叶斯知识追踪实时推出来的。 「我该学什么」交给它，你只管看懂。
主要工作：
  1. 向量检索定位与修复（核心技术点）：排查「向量检索已启用但排序无效果」，定位根因为 nomic-embed-text 未按官方要求区分文档侧 / 查询侧检索前缀，导致查询被编码进文档空间、余弦相似度整体失真（表现为所有卡分数挤在 0.67 附近、top5 差值 < 0.05）。修复后发现新问题：索引内容已变但卡片 id 集合未变，磁盘上的旧索引仍被当作有效缓存复用 —— 遂将缓存指纹升级为带版本前缀，并约定后续每次变更 embedding 输入都必须升版，避免「改了等于没改」。修复后实测向量召回能命中关键词检索完全漏掉的语义近邻卡。
  2. 图算法落地与踩坑：在自建图上实现 PageRank、Personalized PageRank、介数中心性、Louvain、最短路径、k-core 六个算法。定位并修复 Louvain 聚合阶段的模块度分母错误 —— 社区内部边在聚合后变为自环，若沿用第一阶段的 2m 会使所有增益恒为负，症状是「社区数 == 节点数、每点自成一社区」，修复后 567 节点稳定收敛为 17 个社区。PageRank 刻意不与度中心性混用：造卡产生的 related 关系有噪声，PageRank 抗噪；同时处理悬挂节点秩的均摊回填，避免孤立卡吞掉全图概率质量。
  3. 算法选型与评测边界意识：实现 SM-2、FSRS-4.5、BKT、HLR 四种算法并抽象统一契约，实现热切（环境变量优先、配置次之、写错算法名直接抛错而非静默回落）。构建仿真评测层：同一条遗忘曲线 R(t)=2^(-t/h)、同一随机种子下对 300 张卡做 365 天排期对拍，两个种子复跑验证结论不翻转。实测 FSRS 投入产出最优（效率 0.0186，复习次数较 SM-2 少 20%），HLR 期末留存最高（66.5% vs SM-2 的 56.4%）。主动划清两处能力边界：BKT 不参与排期评测（它答「掌握没」不答「何时复习」）；SM-2 根本不预测留存概率（只有难度因子无概率模型），故概率指标栏它只能缺席。
  4. 分层与缓存决策：算法层不 import core、不依赖服务，可用 python -c "import algo.graph" 离线对拍；图结构缓存键携带文件 mtime，造卡后自动失效。关键决策：用户掌握度 level 绝不进图缓存 —— 节点边完全由卡片集决定、与用户无关，而 level 属个人数据，混入会造成 A 读到 B 的缓存（越权）。
  5. 降级可见性设计：MySQL / PostgreSQL / Redis 三层均实现「装不上就降级」，且降级状态一律打到启动横幅。原因是静默降级比崩溃更危险 —— 曾出现 PG 连不上时复习记录静默落盘 JSON、Redis 失效时缓存悄悄退化为进程内存，而启动日志一片安静，看似正常实则数据链路已断。横幅只打不依赖登录上下文的事实，个人口径数字交给带 token 的接口。
  6. 鉴权模型修正：将「是否需要鉴权」的判定标准从读写操作改为「响应是否包含个人数据」。读写粒度判断会漏掉那些 GET 但返回他人学习记录的接口 —— 判定依据应该是数据归属，不是 HTTP 方法。迁移至 PyJWT 零依赖方案（固定 algorithms=['HS256']，避免算法混淆攻击）。

技术点展开 · 面试逐条讲（每点 90 秒）

★★★ 1. 向量检索：症状是「开了但没效果」，根因是编码空间错了
症状　接上 nomic-embed-text 后接口正常返回、索引也建了（4.1MB），但排序没有效果 —— 所有卡相似度分数全挤在 0.67 附近，top5 之间差距不到 0.05。
难点　这个症状极具欺骗性：接口不报错、日志不告警、索引文件存在。任何只看「有没有报错」的检查都会判定这里正常。
根因　nomic-embed-text 是拿 Matryoshka + 检索任务微调过的模型，官方用法硬性要求建索引前缀 search_document:、查询前缀 search_query:。原实现两边共用同一函数且都不加前缀 —— 相当于把查询也编码进文档空间，余弦相似度整个量纲失真。
修复后的二次问题（最值得讲的地方）　加前缀后索引内容变了，但卡片 id 集合没变，而缓存指纹只按 id 集合算 —— 磁盘上那份没前缀的坏索引被当成有效缓存继续加载。改前缀等于没改，而且不报任何错。
修法　缓存指纹改成带版本前缀（v2|card1|card2|…），并立下约定：以后每次动 embedding 输入（换模型、改文本拼法）都必须升版，否则改的永远是缓存。
为什么值钱：同时展示四件事 —— 能识别「无异常不等于正确」这类静默失效、知道官方模型有必须遵守的约定、会为修复付代价（缓存失效）、并把教训写成规则而不是只修一次。
★★★ 2. Louvain 聚合阶段：分母口径错了，症状伪装成「算法失效」
症状　社区发现跑出来后社区数 == 节点数，每张卡自成一社区，完全没分块。
为什么诊断有难度　模块度公式里 2m 是「图的总边权」，很多实现只在入口算一次。第一阶段（贪心移动）确实对，但第二阶段会把整个社区聚合成超点，社区内部的边全部变成自环。经典模块度定义里自环按 2×self 计入总边权，所以第二阶段的 2m 必须重算。
沿用第一阶段 m2 → 分母偏小 → 所有节点模块度增益恒为负 → 一个都搬不动 → 每点自成一社区
修复　2m 每轮重算，聚合阶段额外加上 2 × Σself。
延伸取舍　经典 Louvain 靠随机遍历打破对称，结果不可复现 —— 同一份数据两次跑可能给出不同分块，测试会间歇性挂，界面上「社区」会莫名变一次。改成按 id 排序确定性遍历，用那点随机性换稳定性。416 节点单线程 < 0.5s，不需要更快的实现。
为什么值钱：证明你不是在调库，而是在读实现、算公式、定位到「分母该是什么」这一层。同时展示「知道标准实现哪里会坑」和「主动做有意识的性能 / 稳定性取舍」。
★★★ 3. 图缓存：判断「哪些数据是个人数据」
架构决策　图缓存 key 是 (category, subject)。判定「为什么能缓存」时明确写下约束：节点和边完全由卡片集决定、与用户无关；而掌握度 level 是从 progress 贴上去的个人数据，绝不能进这个缓存 —— 否则 A 的缓存会被 B 读到，正是数据隔离刚修掉的那类越权 bug。
关联的坑　缓存失效判定不能只看 TTL，也不能只看某一个目录的 mtime —— 造卡脚本可能只写 store 不碰 data。mtime 必须取 data/*.js、data/、store/ 三个来源的最大值。
为什么值钱：体现的是威胁模型意识 —— 不是「加了缓存性能好了」，而是「我知道这个缓存一旦画错边界会造成什么后果，所以我在代码里立了界」。面试里讲这个比讲缓存命中率提升 10 倍有分量得多。
★★☆ 4. 降级必须可见：静默降级比崩溃更危险
踩过的坑　ALGO_STORE=pg 连不上时，复习记录静默落进 JSON 文件；Redis 连不上时掌握度缓存悄悄退化成进程内存。两种情况启动日志都一片安静 —— 「能跑、没报错」，但数据链路已经不是配置的那个了。
判断标准　对于依赖可选的系统，「装不上就降级」是对的（不能因为没装 PG 就整个服务起不来），但降级必须让使用者看得见。所以三层的 degraded() 全部接到启动横幅。
顺带一条边界　横幅只打不依赖登录上下文的事实。曾想打「今日待复习 N」，但进度已是 per-user 的，启动时没有登录用户只能读匿名桶（永远为空），这个数字会显示成「全库卡数」，看着像 bug。个人口径数字交给带 token 的接口。
为什么值钱：展示的是工程价值观，而且是可以直接迁移到任何团队的技术判断。讲「我的项目可以降级，但降级一定可见」比讲「我用了 Redis」有价值。
★★☆ 5. 鉴权：判定标准是数据归属，不是 HTTP 方法
原判定　按读写操作区分 —— GET 公开、写操作要 token。
为什么错　会有「GET 但返回他人学习记录」的接口被漏掉。真正的判定依据是响应里有没有个人数据，不是请求用了什么方法。
修正后　/api/review/due 这类纯 GET 接口因返回个人复习队列而必须鉴权。实现上迁移到 PyJWT 零依赖方案（不引第三方 JWT 库，固定 algorithms=['HS256'] 避免算法混淆攻击）。
更隐蔽的坑　光给表加 user_id 列不等于做了隔离 —— ON DUPLICATE KEY UPDATE 只看主键，主键里没有 user_id 的话写路径会静默覆盖。两个表的个人数据主键必须都带 user_id。
★★☆ 6. 评测的边界：敢说「我的评测测不出什么」
结论　FSRS 效率最优（0.0186），但我没把系统默认切成 FSRS。
理由　仿真评测的 ground truth 是我自己造的遗忘曲线，它能回答「同一条曲线下谁排期排得好」，不能回答「谁对你的学生最好」。FSRS 排期次数少 20% 是因为它认为你记得住 —— 如果这个判断偏乐观，实际留存会掉。真正的判据是真实回忆成功率，需要真实 review log 积累。
两处主动划清的边界
· BKT 不参与排期对比（它答「掌握没」不答「何时复习」，硬让它排期是塞进不属于它的角色）
· SM-2 根本不预测留存概率（只有难度因子和间隔，没有概率模型），logLoss / AUC 这栏它只能缺席 —— 这不是 bug，是算法真实的能力边界
还有一条自我批评　三者 AUC 都在 0.51 附近（接近随机），说明合成曲线下概率预测的区分度有限。评测的价值在排期效率对比，不在概率预测准确度。
为什么值钱：校招面试里绝大多数候选人只会说「我实现了 XX 算法」。能说清「我的评测测不出什么、为什么不急着切」的候选人，面试官会立刻区别出来。
