## ★ 先看清区别在哪

上一版这样写（**错**）：

> 1. 知识图谱构建：将 527 张卡片按四层建模，沉淀 819 节点 / 2713 边有向图，
>    实现 PageRank、Louvain 等 6 个图算法。

面试官读到的是：**他调了 6 个算法**。→ 「会用现成的东西」，顶多算熟悉。

这一版这样写（**对**）：

> 1. 知识图谱与图算法：Louvain 社区发现发现经典实现的结果不可复现（随机遍历
>    打破对称），改为按 id 确定性遍历；定位到聚合阶段「社区数 == 节点数」的
>    根因是模块度分母 2m 未随自环重算 —— 聚合后社区内部边变成自环，若沿用
>    第一阶段的 m2 会导致所有增益恒为负、一个都合并不了。修复后全图
>    稳定收敛到 17 个社区（416 张卡时实测，现库已扩到 527 张）。

面试官读到的是：**他知道标准实现的坑在哪、会用「症状→分母口径」这种思路定位
问题、并且知道为什么放弃随机性换确定性**。→ 这是**能力**，不是技能。

**本项目最强的技术点排序（面试就讲这些）：**

| 级别 | 技术点 | 为什么值钱 |
|---|---|---|
| ★★★ | 向量检索「查询被编码进文档空间」 | 症状极难定位（分数全挤在 0.67），病因是漏了官方要求的检索前缀，且**修复有代价**——索引指纹必须同步升级，否则改了等于没改 |
| ★★★ | Louvain 聚合阶段 2m 未重算 | 标准实现的经典坑，症状伪装成「算法失效」，实际是模块度分母口径错 |
| ★★★ | 图缓存不存用户 level | 架构级安全决策，涉及「哪些数据是个人数据」的判断，写错就是越权 |
| ★★☆ | 降级必须可见（横幅） | 工程判断：静默降级比崩溃更危险 |
| ★★☆ | 鉴权判定从「读写」改为「响应有无个人数据」 | 懂「鉴权的本质是数据归属」而不是「拦截 API」 |
| ★★☆ | 三算法对比 + 双 seed 验证 | 知道「仿真评测的结论只在同一条曲线下成立」，敢划清能力边界 |
| ★☆☆ | 邻域展开按语义终止 | 体现「理解数据语义而非机械设参」 |

## 版本 A：主推版（推荐，AI Agent / 后端岗通用）

```
2026/09-至今        智径 EduPath · 多 Agent 自适应学习平台        全栈开发

技术栈：Python、FastAPI、LangGraph、LangChain、Ollama（qwen3:8b /
        deepseek-r1:7b / nomic-embed-text）、MySQL、PostgreSQL、Redis、
        Vue3、Vite、Element Plus、ECharts、JWT

项目描述
  面向计算机与考研知识点的**多 Agent 自适应学习平台**。市面上的刷题App
   都假设你知道自己要学什么，于是只能按固定顺序推送；而真实情况是多数人
   连「从哪开始、卡住了该往哪走」都判断不了，卡在一道题上常常是因为它的
   三个前置知识点里有一个没懂。
   平台的做法是先把知识点之间的**先修依赖**显式建成图，再由三个 Agent 分工：
   造卡 Agent 把教材和文档转成结构化卡片、问答 Agent 负责答疑与讲解、
   规划 Agent 根据你的掌握度决定下一步学什么。掌握度不是自己填的等级，
   而是由复习行为经贝叶斯知识追踪实时推出来的。
   「我该学什么」交给它，你只管看懂。


主要工作：
1. 向量检索定位与修复（核心技术点）：排查「向量检索已启用但排序无效果」，
   定位根因为 nomic-embed-text 未按官方要求区分文档侧 / 查询侧检索前缀，
   导致查询被编码进文档空间、余弦相似度整体失真（表现为所有卡分数挤在
   0.67 附近、top5 差值 < 0.05）。修复后发现新问题：索引内容已变但卡片
   id 集合未变，磁盘上的旧索引仍被当作有效缓存复用 —— 遂将缓存指纹升级为
   带版本前缀，并约定后续每次变更 embedding 输入都必须升版，避免
   「改了等于没改」。修复后实测向量召回能命中关键词检索完全漏掉的
   语义近邻卡。

2. 图算法落地与踩坑：在自建图上实现 PageRank、Personalized PageRank、
   介数中心性、Louvain、最短路径、k-core 六个算法。定位并修复 Louvain
   聚合阶段的模块度分母错误 —— 社区内部边在聚合后变为自环，若沿用第一阶段
   的 2m 会使所有增益恒为负，症状是「社区数 == 节点数、每点自成一社区」，
   修复后全图稳定收敛为 17 个社区。PageRank 刻意不与度中心性混用：
   造卡产生的 related 关系有噪声，PageRank 抗噪；同时处理悬挂节点秩的
   均摊回填，避免孤立卡吞掉全图概率质量。

3. 算法选型与评测边界意识：实现 SM-2、FSRS-4.5、BKT、HLR 四种算法并
   抽象统一契约，实现热切（环境变量优先、配置次之、写错算法名直接抛错
   而非静默回落）。构建仿真评测层：同一条遗忘曲线 R(t)=2^(-t/h)、同一
   随机种子下对 300 张卡做 365 天排期对拍，两个种子复跑验证结论不翻转。
   实测 FSRS 投入产出最优（效率 0.0186，复习次数较 SM-2 少 20%），HLR
   期末留存最高（66.5% vs SM-2 的 56.4%）。**主动划清两处能力边界**：
   BKT 不参与排期评测（它答「掌握没」不答「何时复习」）；SM-2 根本不预测
   留存概率（只有难度因子无概率模型），故概率指标栏它只能缺席。

4. 分层与缓存决策：算法层不 import core、不依赖服务，可用
   `python -c "import algo.graph"` 离线对拍；图结构缓存键携带文件 mtime，
   造卡后自动失效。**关键决策：用户掌握度 level 绝不进图缓存** ——
   节点边完全由卡片集决定、与用户无关，而 level 属个人数据，混入会造成
   A 读到 B 的缓存（越权）。

5. 降级可见性设计：MySQL / PostgreSQL / Redis 三层均实现「装不上就降级」，
   且降级状态一律打到启动横幅。原因是静默降级比崩溃更危险 —— 曾出现
   PG 连不上时复习记录静默落盘 JSON、Redis 失效时缓存悄悄退化为进程内存，
   而启动日志一片安静，看似正常实则数据链路已断。横幅只打不依赖登录上下文
   的事实，个人口径数字交给带 token 的接口。

6. 鉴权模型修正：将「是否需要鉴权」的判定标准从读写操作改为「响应是否包含
   个人数据」。读写粒度判断会漏掉那些 GET 但返回他人学习记录的接口 ——
   判定依据应该是数据归属，不是 HTTP 方法。迁移至 PyJWT 零依赖方案
   （固定 algorithms=['HS256']，避免算法混淆攻击）。
```

3. 工具调用的数据隔离：QA 工具签名不能带 user_id（要暴露给模型），

   零进度用户看到的待复习队列是设计而非数据泄漏。
4. 间隔重复算法选型：实现 SM-2 / FSRS-4.5 / BKT / HLR 四算法 + 统一契约

5. 图谱前端与一致性治理：Vue3 + ECharts 力导向视图支持多级筛选与社区着色。
   修复「图与统计口径不一致」（社区按全库算、图按筛选算，导致 15 个社区
   13 个命名失效）—— 判定标准是：只要前端拿 A 的结果反查 B 的 id 集合，
   A 和 B 必须来自同一次计算。修复后 13/13 全部正常。
6. 降级可见性与存储分层：MySQL / PG / Redis 三层均支持降级并打到启动横幅；

## ★ B 版专属追问预案（你选了 B 版，这些必须准备）

B 版把 ReAct Agent 和混合检索放到最前，面试官的第一批问题会围绕这两块。
**下面 6 问按被问概率排序。**

### Q1「你的 ReAct 和普通问答有什么区别？为什么要多这一套？」

**区别在决策权归谁。** 普通流程（我叫他 flow 模式）是固定管线：
检索 → 拼上下文 → 一次 LLM 调用。快、稳、便宜，但模型只能被动接收我给的东西。
ReAct 模式下模型自己判断「我需要查哪张卡」「需不需要再看关联卡」「知识库够不够、
要不要联网」，循环直到它认为能回答。

**为什么两套都留**：校招面试官问「你为什么用 LangGraph」时，能答出
「我按场景分流了，固定流程覆盖 80% 的问题、ReAct 处理需要多轮检索和外部信息的长尾」
比「因为 LangGraph 流行」强十倍。LangGraph 的真正价值是把状态流转从代码里抽出来 ——
造卡四阶段的流转关系一眼能看清，且每个节点可独立重试。

⚠️ 被追问「那 ReAct 的代价是什么」一定要答：**成本和延迟不可控**。
一次 ReAct 可能调 3~5 轮工具、每轮都过一遍 LLM。所以我保留 flow 作为默认，
只在需要联网或问题明显复杂时才走 ReAct。

### Q2「工具的 docstring 直接给模型看不怕被诱导吗？」

**这是把双刃剑，我认这个风险。** 现在的做法是：docstring 里只写**做什么**，
不写**怎么连数据库**；工具内部自己处理 user_id（ContextVar 注入），
模型既看不到也不需要传用户身份 —— 所以即使模型被诱导调工具，
它也构造不出「查别人进度」这种调用。

**要补的防护**：参数白名单校验（现在靠 pydantic）、以及工具返回值的裁剪
（现在把整张卡返回，token 浪费且可能带出多余字段）。

### Q3「你怎么保证工具不会泄露别人的数据？」

三层验证，不是「我觉得没问题」：
1. **单元层**：直接调 db 函数，指定 A 的 user_id 只能读写 A 的行
2. **线程层**：ContextVar 在实际执行的线程里能读到正确值
3. **接口层**：拿两个真实账号打 HTTP，A 的 token 请求 `/api/review/due`
   只能看到 A 的队列

**一个必须讲清的坑**：`due_list` 的语义是「未标记过 = 待学（永远在队列里）」，
所以**零进度用户看到 15 张卡是设计，不是数据泄漏**。这个如果不主动解释，
面试官很容易误判你越权。

### Q4「混合检索为什么要混合？纯向量不行吗？」

**纯向量会漏掉精确匹配。** 向量擅长语义近邻，但对专有名词、类名、API 名
这种「必须字面精确」的查询反而不如关键词。实测查「HashMap 为什么线程不安全」：
关键词检索 5 条全是 HashMap/LinkedHashMap/ConcurrentHashMap 源码 ——
**它找不到「哈希表如何解决冲突与扩容」**（那才是答案所在），
而向量检索把它排到了第 2 位。反过来向量对错别字和生僻表达更脆弱。

所以是**双路召回再融合排序**，不是二选一。

### Q5「你的 embedding 是自己训的吗？」

**不是，用的是开源的 `nomic-embed-text`，我没微调。**

**但我知道它的局限**：这个模型是拿通用语料（英文为主）训的，
中文技术术语的语义空间没有专门优化。我做了两件事缓解：① 按官方要求加检索前缀；
② 拼接卡片的多字段文本（标题 + 一句话 + 关键词 + 原理拆解）而不是只喂标题。

**更彻底的做法是用领域数据微调 embedding** —— 这是我知道但没做的，
因为需要先攒够真实问答对。

### Q6「LangGraph 你用到什么程度？」

诚实答：**编排层，不是深度使用**。我用到的只有两个：
`StateGraph`（定义节点和流转边）和 `create_react_agent`（预置的 ReAct 循环）。
没有用它做多 agent 协作、没有做 checkpoint/human-in-the-loop、
没有用它做子图复用。

**但我知道它的分层价值** —— 我自己的项目里也照着这个思路分：
`agent/cards/` 里 graph 只负责流转、runtime 负责落盘、router 定 HTTP。
理解这个「编排和执行分离」的思想，比会用某个框架 API 更值钱。

## ★★★ 1. 向量检索：症状是「开了但没效果」，根因是编码空间错了

**症状**：接上 nomic-embed-text 后接口正常返回、索引也建了，但**排序没有效果** ——
所有卡的相似度分数全挤在 0.67 附近，top5 之间差距不到 0.05。

**难点在于这个症状极具欺骗性**：接口没报错、日志没告警、索引文件也有 4.1MB，
看起来「功能已实现」。任何只看「有没有报错」的检查都会判定这里正常。

**根因**：nomic-embed-text 是拿 Matryoshka + 检索任务微调过的模型，官方用法硬性要求
建索引时每条文本前缀 `search_document: `、查询时前缀 `search_query: `。
我原来的实现两边共用同一个函数、且**都不加前缀** —— 相当于把查询也编码进了
文档空间，余弦相似度的整个量纲都失真了。

**修复后的二次问题（这才是这段最值得讲的地方）**：加前缀后索引内容变了，
但**卡片 id 集合没变**，而缓存指纹只按 id 集合算 —— 于是磁盘上那份**没有前缀的
坏索引**被当成有效缓存继续加载。我改前缀这件事等于没改，而且**不会报任何错**。

**修法**：把缓存指纹改成带版本前缀（`v2|card1|card2|...`），并在代码注释里
立下约定：以后每次动 embedding 输入（换模型、改文本拼法）都必须升版，
否则改的永远是缓存。

**这个点为什么值钱**：它同时展示了四件事——能识别「无异常不等于正确」这类
静默失效、知道官方模型有必须遵守的约定、会为修复付代价（缓存失效）、
并且把教训写成规则而不是只修一次。

## ★★★ 2. Louvain 聚合阶段：分母口径错了，症状伪装成「算法失效」

**症状**：社区发现跑出来后，**社区数 == 节点数**，每张卡自成一社区，完全没分块。

**为什么这个诊断有难度**：模块度公式里 `2m` 是「图的总边权」，很多实现只在
入口算一次。第一阶段（贪心移动）确实对，但第二阶段会把整个社区聚合成一个
超点，**社区内部的边全部变成自环**。经典模块度定义里自环按 `2×self` 计入总边权，
所以第二阶段的 `2m` 必须**重算**。

**后果**：沿用第一阶段的 m2 → 分母偏小 → 所有节点的模块度增益**恒为负**
→ 一个都搬不动 → 每个节点只能留在自己身上，症状就是「每点一社区」。

**修复**：`2m` 每轮重算，聚合阶段额外加上 `2 × Σself`。

**延伸取舍**：经典 Louvain 靠随机遍历顺序打破对称，结果不可复现 —— 同一份数据
两次跑可能给出不同分块，测试会间歇性挂，界面上「社区」会莫名变一次。
我改成**按 id 排序确定性遍历**，用那点随机性换稳定性。416 节点单线程 < 0.5s，
不需要更快的实现。

**这个点为什么值钱**：它证明你不是在调库，而是在读实现、算公式、定位到
「分母该是什么」这一层。而且同时展示了「知道标准实现哪里会坑」和
「主动做有意识的性能/稳定性取舍」。

## ★★★ 3. 图缓存：判断「哪些数据是个人数据」

**架构决策**：图结构缓存的 key 是 `(category, subject)`，value 是
`(时间戳, nodes, edges)`。判定「为什么能缓存」时我明确写下一条约束：
**节点和边完全由卡片集决定、与用户无关；而掌握度 level 是从 progress 贴上去的
个人数据，绝不能进这个缓存** —— 否则 A 的缓存会被 B 读到，正是数据隔离
刚修掉的那类越权 bug。

**关联的坑**：缓存失效判定不能只看 TTL，也不能只看某一个目录的 mtime ——
造卡脚本可能只写 `store` 不碰 `data`。所以 mtime 要取
`data/*.js`、`data/`、`store/` 三个来源的最大值。

**这个点为什么值钱**：它体现的是**威胁模型意识** —— 不是「加了缓存性能好了」，
而是「我知道这个缓存一旦画错边界，会造成什么后果，所以我在代码里立了界」。
面试里讲这个比讲缓存命中率提升 10 倍有分量得多。

## ★★☆ 4. 降级必须可见：静默降级比崩溃更危险

**踩过的坑**：`ALGO_STORE=pg` 连不上时，复习记录**静默落进 JSON 文件**；
Redis 连不上时，掌握度缓存悄悄退化成进程内存。两种情况启动日志都一片安静 ——
「能跑、没报错」，但数据链路已经不是配置的那个了。

**判断标准**：对于依赖可选的系统，「装不上就降级」是对的（不能因为没装 PG
就整个服务起不来），但**降级必须让使用者看得见**。所以我给 MySQL / PG / Redis
三层的 `degraded()` 全部接到了启动横幅上。

**顺带一条边界**：横幅只打**不依赖登录上下文**的事实。曾经想打「今日待复习 N」，
但进度已是 per-user 的，启动时没有登录用户，只能读匿名桶（永远为空），
这个数字会显示成「全库卡数」，看着像 bug。个人口径的数字交给带 token 的接口。

**这个点为什么值钱**：它展示的是**工程价值观**，而且是可以直接迁移到任何
团队的技术判断。面试里讲「我的项目可以降级，但降级一定可见」比讲
「我用了 Redis」有价值。

## ★★☆ 5. 鉴权：判定标准是数据归属，不是 HTTP 方法

**原判定**：按读写操作区分——GET 公开、写操作要 token。

**为什么错**：会有「GET 但返回他人学习记录」的接口被漏掉。真正的判定依据
是**响应里有没有个人数据**，不是请求用了什么方法。

**修正后**：`/api/review/due` 这类纯 GET 接口因为返回个人复习队列而必须鉴权。
实现上迁移到 PyJWT 零依赖方案（不引第三方 JWT 库，固定
`algorithms=['HS256']` 避免算法混淆攻击）。

**顺带一个更隐蔽的坑**：光给表加 `user_id` 列**不等于**做了隔离 ——
`ON DUPLICATE KEY UPDATE` 只看主键，主键里没有 `user_id` 的话写路径会静默覆盖。
两个表的个人数据主键必须都带 `user_id`。

## ★★☆ 6. 评测的边界：敢说「我的评测测不出什么」

**结论**：FSRS 效率最优（0.0186），但**我没把系统默认切成 FSRS**。

**理由**：仿真评测的 ground truth 是我自己造的遗忘曲线，它能回答
「同一条曲线下谁排期排得好」，不能回答「谁对你的学生最好」。FSRS 排期次数少 20%
是因为它**认为**你记得住 —— 如果这个判断偏乐观，实际留存会掉。
真正的判据是真实回忆成功率，需要真实 review log 积累。

**两处主动划清的边界**：
- BKT 不参与排期对比（它答「掌握没」不答「何时复习」，硬让它排期是塞进不属于它的角色）
- SM-2 根本不预测留存概率（只有难度因子和间隔，没有概率模型），所以 logLoss/AUC
  这一栏它只能缺席 —— 这不是 bug，是算法真实的能力边界

**还有一条自我批评**：三者 AUC 都在 0.51 附近（接近随机），说明合成曲线下
概率预测的区分度有限。评测的价值在排期效率对比，不在概率预测准确度。

**这个点为什么值钱**：校招面试里绝大多数候选人只会说「我实现了 XX 算法」。
能说清「我的评测测不出什么、为什么不急着切」的候选人，面试官会立刻区别出来。
