## 0. 一句话现状

**内容侧（卡片 + 复习 + 文档 + 图谱 + Web 端）已经完整可用，学习者模型侧（诊断 + 路径决策 + 评测）一行没写。**

前端已从零构建的单文件 HTML 迁到 Vue 3 工程（`web/`），后端是 FastAPI 单实现，
存储层可在 JSON / MySQL 之间切换。真正缺的不是页面，是**学习者的状态** ——
现在系统知道「有哪些卡、谁该复习」，但不知道「你哪里不会、下一步该学什么」。

## 3. 后端：单实现（FastAPI）

只有 `run.py` 一个入口。以前还有一个零依赖版 `server.py`（纯标准库 http.server），
**2026-09-26 已移除** —— 鉴权改用 PyJWT 之后它名不副实。

```bash
python back_study/run.py 8080          # 主用
python back_study/run.py 8080 --lan    # 手机同 WiFi 访问
```

### 移除零依赖版时暴露的一个旧洞（值得记住）

`check.js` 的存储一致性对照一直请求 `?limit=1000`，而 `/api/review/due` 的
`limit` 上限是 **500**（`learning.py`：`Query(50, ge=1, le=500)`）→ 直接 400。
旧的零依赖版不校验这个上限、照常返回，于是那份对照**一直是拿空队列比空队列**，
还打印一句 `SKIP` 假装没事。零依赖版一移除，洞才露出来。

> **两套实现互为对照有个前提：不一致要能被看见。**
> 宽松的那套会帮严格的那套把错误吞掉 —— 这跟「互相校验」的初衷正好相反。

`/api/agent/*` 是唯一一组**可选依赖**端点：没装 langchain 时服务照常起，
调用才返 503 并提示怎么装。它是唯一用 `async def` 的路由 —— 单次调用几十秒，
同步 def 会占满 40 槽的线程池，所以走 `asyncio.to_thread()`。

`/api/roles`、`/api/plan` 不一样：**它们不碰模型**，只把 `data/roles.js` 和卡片库
对账（岗位要的技能词在不在库里、卡掌握到什么程度），所以走同步 `def`，几十毫秒。

#### `POST /api/agent/ask` 的请求体（记忆在哪一层）

```jsonc
{
  "question": "那第二个呢",
  "mode": "flow",              // flow = 固定检索流程；react = 模型自己调工具
  "stream": false,             // true 走下面的 SSE
  "history": [{"role":"user","content":"GIL 是什么"},
              {"role":"assistant","content":"..."}],   // L1，后端超预算自动裁剪
  "profile": {"role":"Java 后端","topics":[],"weak":[]} // L3，不传就用服务端存的
}
```

SSE 帧格式（**改了必须和 `web/src/api/agent.js` 同步**）：

| 帧 | 含义 |
|---|---|
| `data: <文本>` | 正文增量，换行转义成 `\\n` |
| `event: sources` + data | 这次引用的卡片 id，JSON 数组（生成结束后才有） |
| `event: done` | 正文流结束 |
| `event: error` | 出错，data 是错误信息 |

### 保契约的五条（改接口前必读）

1. **`RequestValidationError` 统一返回 400。** 前端到处是 `if (status === 400)`，FastAPI 默认返 422 会让所有校验提示失效。
2. **端点写同步 `def`，不要 `async def`。** db 是同步 IO，`async` 会堵死事件循环。
3. **静态挂载最后挂。** 先挂 `/` 会把 `/api/*` 一起吃掉。
4. **`/api/llm/status` 返 `ok:false` 时 HTTP 仍是 200。** 它是「可选能力没开」不是故障。
5. **改完接口跑 `node back_study/scripts/check.js`。** 它起临时服务打 39 个端点，
   再把到期队列用 json / mysql 各算一遍逐位比 —— 这一条是存储层最容易悄悄坏的地方。

### 间隔调度：算法在 `algo/`，db 只转发

`core/db.py:schedule()` 里**不写算法**，只有一行转发到 `algo.get()`。
换算法改配置（`ALGO=fsrs` 环境变量或 `config.local.json`），数据层一行不动。

- 契约：`schedule(prev, level) -> rec`，rec 固定 6 个键
  `level / interval / ef / reps / nextAt / updatedAt`。
  **多一个键都会被 MySQL 静默丢掉**（`progress` 表就是这 6 列），加字段先改存储层。
- 现有三个算法：**SM-2**（默认，纯规则）· **FSRS-4.5**（记忆稳定性，
  复用 `ef` 存难度 D、`interval` 反解 S）· **BKT**（贝叶斯知识追踪，
  复用 `ef` 存掌握度 p∈[0,1]，用 p 反推间隔，见 `algo/bkt.py`）。
- 三个算法的 `ef` **含义各不相同**（难度因子 / 难度 D / 掌握度），
  每个算法都在 `ef_note` 里声明了，别看到 2.5 就当难度因子。
- 间隔有统一上限 `MAX_INTERVAL = 5 年`：SM-2 的间隔是指数增长的，
  不夹住的话连标几十次「会」之后 `date + timedelta` 会溢出 → 整个请求 500。
- 算法名写错**抛异常**，不静默退回默认 —— 配置拼错却假装成功比启动失败更糟。
- `algo/` 不反向依赖 core：拿一个 dict 就能跑，调参和单测不用起服务。
- 对拍：`python back_study/algo/demo.py`（同序列比两个算法的复习次数）。

### 复习事件流（知识追踪的共同地基）

`set_level()` 是覆盖式写入，只留最新状态、不留历史 —— 而 BKT / DKT / AKT 吃的
都是 `(用户, 知识点, 时刻, 对错)` 事件流。所以标记进度时**双写**：

```
set_level(cid, level, user_id) → progress_put(状态，覆盖) + events_append(事件，追加)
```

- 事件落在 `core/algostore/`（PG `review_events` 或 JSON），和业务库分开。
- 不传 `user_id` 的老调用不写事件 —— 掌握度是 per-user 的，没用户就没法归因。
- ★ 2026-10-03 起 `user_id` **同时是进度归属**，不再只是事件归属。
  以前 progress 是全局一份，探针账号写一次就把真人覆盖掉（实测踩过：
  6 行进度全被顶掉，且没有任何日志）。

### 数据隔离（progress / notes 的 user_id）

进度和笔记是**个人数据**，两张表都按 `user_id` 分桶：

| 层 | 结构 |
|---|---|
| MySQL | `progress` PK `(user_id, card_id)`；`notes` PK `(user_id, id)`；`user_id=''` 是匿名桶 |
| jsonfile | `progress.json` = `{uid: {cid: rec}}`；`notes.json` = `{uid: [note]}` |
| 业务层 | `db.get_progress(user_id)` / `set_level(cid, level, user_id)` / `due_list(..., user_id)` 等**一律收user_id** |
| Agent | QA 工具签名给模型看、不能加参数 → `tools.set_current_user(uid)` + `runtime.ask_full(..., user_id)` |

**两条踩过的坑，改这一层时必须一起看**：

1. **光加列不改主键 = 没隔离。** `INSERT ... ON DUPLICATE KEY UPDATE`
   判重只看主键/唯一索引。主键还是`(card_id)` 的话，两个用户复习同一张卡
   写的还是同一行 —— 加了 `user_id` 列、查询也带了过滤，**写**那一步仍在
   静默覆盖。读路径看着全对，是这类改动最隐蔽的失败方式。
   `_REKEY_TABLES` 就是干这个的，别删。
2. **`LEFT JOIN` 上的user_id 条件不能省。** 只在 `WHERE` 里加
   `p.user_id=%s`，「没标记过」的卡 `p.user_id` 是 NULL，会被一起滤掉 →
   未标记的卡从队列消失（LEFT JOIN 被降级成 INNER JOIN 的典型症状，不报错、
   只是队列变短）。条件必须写在 `ON` 子句里。

**鉴权口径不变**：看的是「响应里有没有个人数据」，不是方法名带没带 put。
- 「模糊」按**答错**处理：BKT 只吃二值，把模糊当成学会的代价是这张卡可能
  永远不再出现，代价大得多。
- 攒够数据后：`db.fit_bkt(user_id)` 就能从你自己的记录里拟合出四个参数。
  门槛 8 个知识点 / 30 条记录，不够时拒绝拟合并返回默认参数。
- BKT 的掌握度走 `cache` 缓存（算一次要重放整条事件流，而队列和看板每次都读）。
  ★**重新拟合后必须清缓存**：参数换了，之前算的掌握度全是旧参数下的值，
  不清就会出现「明明重新拟合了，查出来却没变」。

### 校验

```bash
node back_study/scripts/check.js
```

一次跑完：卡片数据 → 网页内联脚本 → `pyFiles` 清单里的 Python 文件编译（+
pyflakes 建议）→ **API 冒烟**（端点数见上面的端点全表）→ **json 与 mysql 的到期
队列逐位对照**。动接口、动存储、动数据必跑。

★ 加新 `.py` 文件**必须回补 `check.js` 里的 `pyFiles` 清单**（手维护），
漏了就不会被编译检查。队列对照会先比对两边的 `level` 输入，**数据不同步时
打印 SKIP 并说明，不算失败** —— 之前两边都降级到 json、读同一个文件，
等于自己跟自己比，绿了也是假的。

## 4. 存储层：可切换、可降级、可验证

`core/store/` 三个后端：

| 后端 | 触发条件 | 用途 |
|---|---|---|
| `jsonfile` | 默认，或 mysql 不可用时的降级目标 | 零配置跑起来 |
| `mysql` | `config.local.json` 里 `STORE=mysql` | 正式用 |

**切换只改一个字段**，业务代码零改动（`core/db.py` 只负责算，`store/` 只负责存）。

```jsonc
// back_study/config.local.json
{ "STORE": "mysql",
  "MySQL": { "host": "127.0.0.1", "port": 3306, "user": "root", "password": "…", "database": "study_cards" } }
```

环境变量 `STORE` 优先级高于配置文件。

### 七张表

`cards`（内容查询副本）· `progress` · `notes` · `documents` · `drafts` · `meta` · `users`

### ★ 降级必须看得见

缺 pymysql / MySQL 没起 / 表没建 → **自动回退 JSON 照常服务**，但：

- 启动横幅打 `!!`
- `/api/storage` 的 `degraded` 字段写明原因
- 运行状态页顶部出现红色提示条

**悄悄回退 = 用户以为在写数据库，其实写进了文件。** 这条比报错重要。

⚠️ **降级判断是启动时算一次、之后不再复算的。** 所以「MySQL 没起时启动的服务，即使后来 MySQL 起来了，它这辈子都写 JSON」。
换存储或重启 MySQL 之后，**必须重启后端进程**。运行状态页显示
「配置要求 mysql / 实际后端 JSON 文件 / 与配置不一致」就是这个状态。

### 内容 vs 状态

`data/*.js` 是**内容**（git 管，权威）。MySQL 的 `cards` 表只是**查询副本** ——
改了源文件跑 `dbseed.py --sync`，指纹不符时接口会报 `stale:true` 并**回落读文件**，
不会端出旧内容。

### 加一张新表要同步改三处（最容易漏）

1. `core/store/schema.sql` 的 DDL
2. `core/store/mysql.py` 的 `_DDL`
3. `core/store/jsonfile.py` 的同名方法 **+ `dbseed.py --import-json` 的文件清单**

第 3 处漏掉的后果最隐蔽：`users` 表就是这么漏的 —— 服务正常起、卡片正常看，
**一点登录才 500**。详见第 12 节踩坑 1。

### dbseed.py

```bash
python back_study/scripts/dbseed.py --status        # 当前用哪个后端、为什么降级
python back_study/scripts/dbseed.py --sync          # 建表 + 同步内置卡
python back_study/scripts/dbseed.py --import-json   # 把 JSON 存量单向搬到 MySQL（先备份 .bak）
python back_study/scripts/dbseed.py --drop --yes    # 删库重来
```

### 第二个库：PostgreSQL（`core/algostore/`）—— 算法 + AI 的数据

业务主数据在 MySQL，**算法和 AI 的数据在 PG**，两个库各管一摊：

| | MySQL `study_cards` | PG `study_algo` |
|---|---|---|
| 存什么 | 卡片内容副本、进度、笔记、用户 | 复习事件流、掌握度、拟合参数 |
| 为什么 | 已经在跑，主业务链路 | JSONB 存参数（结构会变，不用改表）、后期 pgvector 做 RAG |

- 切换：`ALGO_STORE=json`（默认）| `pg`，和 `STORE` 同一个套路，降级同样**必须看得见**。
- 三张表：`review_events`（append-only 事件流）/ `mastery`（{user,kc} → p）/ `algo_params`（JSONB）。
- 建表是幂等的，第一次连上自动建，不用手动跑脚本。
- 本机：PG 16.15 在 5432，库 `study_algo`，账号 postgres / 密码写在
  `config.local.json`（不进 git）。

### 缓存层（`core/cache.py`）

Redis 优先，没装 / 没起 / 密码不对就**降级到进程内存**，服务照常跑，
但降级原因会写进 `degraded()` 让启动横幅打出来。

- 本机：`E:\Redis\redis.conf`，`requirepass 123456`，内存上限 256MB，数据在 `E:\Redis\data`。
- 启动：`E:\Redis\start.bat`（`start.vbs` 无窗口拉起，关掉控制台也不停）。
- **内存降级只在当前进程内有效、重启即失效、多进程不共享** —— 它是「没 Redis 也能
  开发」的兜底，不是等价替代。
- 所有 key 带 `study:` 前缀，免得和本机别的练手项目撞车。

## 6. 卡片契约

必填字段：

```
id · domain · category · subject · topicPath[] · title · oneLine · analogy
why · mechanism[] · diagram · interviewQ[] · keywords[] · scene[](≥2) · tags[] · related[]
```

- `category + subject` 必须在 `data/catalog.js` 里，否则导航选不到
- `related[].kind` 只允许 `prereq | extends | compare`，**且必须带 `note`**
- `diagram` 三选一（严格 JSON）：
  `pipeline{stages[],frames[]}` / `state-machine{nodes[],edges[],frames[]}` / `snapshot{panels[],frames[]}`

**加科目只改一处：`data/catalog.js`。** 卡片文件扔进 `data/*.js` 会被 `core/db.py` 自动扫到，
前端的分类树走 `GET /api/catalog` 现取 —— 所以不需要改前端任何一行。

**加岗位改一处：`data/roles.js`。** 同样是配置不是状态，读法也和 catalog 一样
（严格 JSON 字面量 + `raw_decode`）。一个岗位 = 几个技能组：

```js
{ "id": "java-backend", "name": "Java 后端开发", "desc": "…",
  "skills": [ { "subject": "java", "weight": 3, "keywords": ["JVM","并发","…"] } ] }
```

- `subject` 必须在 `catalog.js` 里；`weight` 只用来排组顺序（1-3）
- `keywords` 是这个岗位真正的考点，`GET /api/plan` 拿它们**逐个对卡片库**——
  所以缺口报的是「没有『向量检索』的卡」，而不是「AI 工程科目没学」。
  子科目有卡 ≠ 覆盖了岗位要的那条考点，这正是按技能词算的原因。
- ⚠️ 导出必须是 `module.exports = { ROLES: … }`（对象）。导出**数组**会被
  `check.js` 当成卡片文件校验，报一堆 MISSING field。

## 7. AI 精读（唯一的可选层）

`core/llm.py` 三档：`AI=off` → 云端（`LLM_API_KEY`）→ 本地 Ollama 兜底。
**关掉它不影响任何核心功能**，只是少一个按钮（详见 DEPLOY.md）。

- 判断可用性**只认 `GET /api/llm/status`**，不要读 `/api/health` 的 `llm` 字段 ——
  后者的定义是 `bool(LLM_API_KEY)`，只表示「配了云端 key」。见踩坑 7。
- **精读必须逐章调。** 批量调会把 A 章的内容安到 B 章上。
- 推理模型（deepseek-r1）必须传 `think:false`，否则烧光 token 且正文为空。

### AI Agent 层（`agent/`，LangGraph + 本地 Ollama）

同样是可选依赖：`langgraph` / `langchain` / `langchain-ollama` 在
`requirements.txt` 的可选段，不装也能起服务。

```
config.py  参数      model.py  模型      tools.py  能做什么
nodes.py   每步      graph.py  顺序      runtime.py 怎么跑
demo.py    命令行     app/routers/agent.py  HTTP 接口
```

**★ 所有 langchain 的 import 都写在函数内部。** 模块级 import 一次 2-3 秒，
放进启动路径等于每次冷启动都替 AI 买单，而这个接口可能一天没人调。

★ **别用 LangGraph 的场景**：一问一答（结构化抽取）。判断标准是
**流程里有箭头吗？没有就别上** —— 那种用 `core/llm.py` 三个函数写完就对，
套 LangGraph 是纯负担。

#### 三层记忆，各自归谁存

| 层 | 内容 | 存在哪儿 | 怎么进提示词 |
|---|---|---|---|
| L1 会话多轮 | 本次对话的上几句 | **前端**持有，随 `history` 发过来 | `runtime.trim_history()` 按 1500 字预算从最旧丢起，保最近 2 轮；flow 压成【此前对话】，react 直接接在消息列表前 |
| L2 检索上下文 | 这次召回的卡片 + 上一句用户话 | 每请求现算，不落盘 | `nodes.retrieve` 拼进【资料】 |
| L3 长期档案 | 目标岗位 / 常问主题 / 薄弱卡 | `data/store/profiles.json`（按登录用户，**不进 MySQL**） | `runtime.format_profile()` 变成一条 system 消息 |

L3 刻意不进存储契约：加表要改 base / jsonfile / mysql / schema 四处，换来的只是
「档案跟着库走」，而它全是派生数据，丢了能自己积累回来。等 progress/notes 做
per-user 隔离时再一起搬。

#### 回答里不许出现卡片 id（用户明确反馈过）

三道关，缺一道就漏：

1. **提示词**：`ANSWER_SYS` / `REACT_SYS` 明写「不输出 id、【xxx】、JSON、工具名」，
   检索资料也改成用**标题**而不是 id 做标记。
2. **后端清洗**：`runtime.clean_answer()` 把 `【some-id】`、`卡 ID：xxx`、
   内嵌 JSON、`引用卡片：…` 行剥掉 —— 8B 模型照抄提示词的病，靠说没用。
3. **前端镜像**：`web/src/api/agent.js:cleanAnswer()`。流式是**边生成边渲染**的，
   后端只能等生成完再洗，那时候用户已经看见了。

react 模式的 `sources` 有两个来源：随问题注入的底料（`runtime._react_ground()`，
和 flow 的 `retrieve` **同一套检索**）+ 工具返回（`_ids_in`），最后按真实卡 id
白名单过滤 —— 模型瞎填的工具参数不会变成引用。flow 模式的 `sources` 由 `retrieve`
直接写 state。底料为什么由代码代搜：光在 `REACT_SYS` 里写"先 search_cards"，
8B 实测两轮都不查，直接凭参数知识答 —— sources 全空，还编库里不存在的卡名。

#### 卡片 Agent（`agent/cards/`，文档 → 草稿卡）

老链路（`/api/llm/enrich` → `/api/llm/to-card`）保留并行；这条是**手动触发**的新链，
一个开关一次跑一章，全部落草稿，发布仍在「生成」页把关 —— agent 不越过生成检查。

**两张图，都是直路 + 一条条件边**（`graph.py`）：

| 图 | 节点 | 说明 |
|---|---|---|
| `refine` | `refine` | 规则先切一版（`importer.structure_items`）→ LLM 精修切分点（`llm.refine_structure`）→ `importer.apply_structure` 合并回正文。扁平下标必须严格等于 `range(n)`，对不上就原样返回，**精修永远只可能变好** |
| `chapter` | `captions → draft → ground →(route)→ retry/end` | VLM 给本章图片出图注（`llm.vlm_caption`，qwen2.5vl:7b）→ 生成卡 → 对齐自检（`llm.align_score` ≥ `CARDS_MIN_ALIGN` 且 keywords 出自原文）→ 不过就把不合格原因喂回去重试，到 `CARDS_MAX_TRIES` 次仍不过：**照样落盘但 `ok:false`**，前端标「需人工把关」 |

三个必须知道的点：

1. **草稿 id 只由 `docId + 章节下标` 决定**（`md5` 前 8 位，`ag-` 前缀），
   `runtime._card_id` 和 `nodes._build_card` 两处必须同源 —— 曾经一边掺章节标题、
   一边掺模型出的卡标题，结果断点续跑永远命不中、图片拷进了另一个 owner 目录。
2. **图片两次拷贝**：解析期原图存 `data/store/media/<docId>/`，正文留 `![](media:名)`
   占位随分章落章；一章的最终卡定稿后才 `copy_media` 到 `card-<卡id>/`，卡片不随
   源文档删除而丢图。`GET /api/media/{owner}/{name}` 登录可读，`<img>` 走 `?t=<token>`。
   发布（`publish`）不再删图，`drop_draft` 只在同 id 没有已发布卡时才清媒体。
3. **幂等 = 断点续跑**：同章重跑直接返回 `skipped:true`；`force:true` 才重新生成。
   一章一卡、一章一请求（多章同跑会互相挤超时，axios 侧单独放宽到 300s/600s）。

端到端证据：`cards_e2e.py`（真模型）—— 结构精修 `refined:true`、两章 grounding
0.38/0.44 通过、VLM 图注生成、`?t=` 200 image/png、无 token 401、重复跑 skipped、
发布 2/2、删文档连图删，23 项全绿。

**想自己动手实现一遍**：见 `docs/AI编排动手路线.md`，8 步从零搭到接进 FastAPI，
每步都标了参考答案在哪个文件、以及实测踩过的坑（10 条）。

## 11. 踩坑索引

每条格式：**症状 → 根因 → 处置**。

### 后端 / 存储

1. **服务正常起、卡片正常看，一点登录就 500**
   → 三个缺口叠在一起：建表只在 `dbseed.py` 里跑（后端启动不建）、可用性探测只查了 `cards` 表、
   `--import-json` 的文件清单里没有 `users.json`。
   → 已修：启动跑一次幂等 `init_schema()`（失败只警告不拦启动）、探测遍历 7 张必需表、账号搬运补齐。
   **注意搬运账号不能直接 `user_put`（在空表上会静默 0 行），要带库里的 id 走 UPDATE。**

2. **`Packet sequence number wrong`**
   → pymysql 连接跨线程复用。→ thread-local + `ping(reconnect=True)`，别用单例。

3. **`ping()` 报 1049「库不存在」**
   → `ping()` 会带 database。→ 初始化脚本用 `ping_server()`，且 `dbseed.py` 必须用 `make_mysql()` 绕开工厂探测，否则永远建不了库。

4. **MySQL 取回数字变成 `Decimal`，接口 500**
   → DECIMAL 字段不转 float 直接序列化会炸。→ 出库前统一 `float()`。

### 前端

5. **vite dev server 的 WebSocket 连不上 / HMR 失效**
   → dev server 只监听了 IPv6（`[::1]:5173`）。Node 18+ 把 `localhost` 优先解析成 `::1`。
   → `vite.config.js` 写死 `host:'127.0.0.1'` + `hmr:{host:'127.0.0.1'}` + `strictPort:true`；浏览器用 `127.0.0.1` 打开。

6. **`504 Outdated Optimize Dep`**
   → `node_modules/.vite` 与重装过的依赖不一致。→ `rm -rf node_modules/.vite` 后重启 dev server。

7. **同一套系统，两个页面显示「AI 可用」/「AI 未启用」**
   → `/api/health` 的 `llm = bool(LLM_API_KEY)` 只表示云端 key；本机跑 Ollama 时它是 false。
   → 前端消费方改为统一读 `/api/llm/status`；判断依据只留一处。

8. **知识图谱画布一片空白**
   → `EChart.vue` 在骨架屏态（`v-show` 隐藏 = 容器 0×0）就 `echarts.init`，
   ECharts 把 0×0 记成画布尺寸，力导向把节点全收敛到原点，之后 `resize()` **不会重算已收敛的布局**。
   柱状 / 饼图会自己摆正，所以只有 force 图中招。
   → 容器有非零尺寸才 init。

9. **环形图右下角多出一个图例**
   → ECharts 判定画不画图例看的是 **`legend` 键存不存在**，不是 `show` 的值。
   `chartBase()` 里只想提供样式的配置让每个图都长出了图例。→ 默认 `show:false`，需要的图显式打开。

10. **页面内容只占左上一小块，右边和下方大片空白**
    → `web/index.html` 里那段「首屏骨架」CSS 把 `body` 设成了 `grid + place-items:center`，
    而它是**全局生效且永不撤销**的，`#app` 就成了被居中的 fit-content grid item。
    → 骨架样式只保留背景色，不碰布局。

11. **菜单项整片消失（`opacity:0`）**
    → `.rise` 用 `animation: ... both`，动画开始前就停在 `opacity:0`。
    → `prefers-reduced-motion` 降级里必须**同时清 `animation-delay`**，只改 duration 不够。

### 截图 / 调试环境

12. **截图是纯白**
    → 本机开着 TUN 代理，chrome 把 `127.0.0.1` 也送去代理了。
    → chrome 加 `--no-proxy-server --proxy-bypass-list=<-loopback>`；curl 加 `--noproxy '*'`。

13. **`.rise` 动画停在半透明，看起来像页面坏了**
    → headless 的 virtual-time 不推进 CSS 动画的合成帧。
    → 加 `--force-prefers-reduced-motion`。

14. **知识图谱在截图里是空的（但真机正常）**
    → 力导向靠 `requestAnimationFrame` 逐帧退火，headless 会在 rAF 一帧没跑时就截图。
    → 加 `--run-all-compositor-stages-before-draw --disable-new-content-rendering-timeout`。

15. **某些页面永远截不出图（PNG 不出现）**
    → 两个原因：① 多个 chrome 实例共用同一个 `--user-data-dir`，新实例把 URL 转交给旧实例后自己退出，
    `--screenshot` 根本不执行；② 输出文件名里带了斜杠（`admin/system` → `_shot/tag-admin/system.png`，
    子目录不存在，写不进去）。
    → **每个页面一个独立 profile**；输出文件名先把 `/` 换成 `_`。

16. **Git Bash 给假信号（反复踩）**
    - `curl -o /dev/null` 退出码是 **23**（Windows 不认 `/dev/null`），请求其实成功了
    - `cd X && cmd &` 里的 `&` 作用于**整条列表**，`cd` 也进了子进程 —— 这解释了「日志明明写了却读不到」
    - heredoc 会把 Python 源码里的**反斜杠转成斜杠**（`\s` → `/s`），正则静默失配、一处都改不到且不报错
    → 探活用 shell 重定向或真实临时文件；后台命令用绝对路径；正则改用纯字符串替换，
      **脚本写成文件再跑，别走 heredoc**。
