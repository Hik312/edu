## 一、这是什么

**一句话**：面向计算机与考研知识点的卡片式学习平台，把 416 张原理卡片组织成
567 节点 / 2114 边的知识图谱，用图算法规划学习路径、用间隔重复算法安排复习，
AI 问答层用 ReAct Agent + 混合检索答疑，全程本地模型部署。

**它解决什么问题**：计算机领域知识点又碎又散——HashMap 挂了连带 GC、JVM、
并发编程全要知道；考研又是另一套体系。碎片化学习的问题是**不知道该先学什么、
学完该接着学什么**。这个项目把知识点之间的**先修关系和语义关联**显式建成图，
再用算法给出路径建议和复习排期。

**三张核心数据流**：

```
造卡流   文档/PDF → LLM 定切分点 → 近重去重 → 草稿池 → 人工审核 → 正式卡 → 图
学习流   选岗位/方向 → 图推荐（PPR）→ 卡片学习 → 标记掌握度 → progress
复习流   间隔重复算法（SM-2/FSRS/HLR）→ 今日队列 → 评级 → 更新间隔 → 事件流 → BKT 拟合
```


## 四、架构分层（最重要的一条约定）

```
app/routers/  →  只做 HTTP：取参数、调 core、返响应。不写业务逻辑
core/         →  数据与业务：db / security / llm / cache
algo/         →  算法：★ 不 import core、不 import 第三方、只用标准库
agent/        →  Agent：编排 LLM 调用，依赖 core 但不被 core 依赖
```

**为什么算法层必须独立**：图算法要调参（阻尼、社区度、边类型权重），
写在路由里就没法离线对拍、没法单测。分层之后一条命令就能验证：

```bash
cd back_study && python -c "import algo.graph; print('ok')"   # 不起服务
python algo/demo.py --list                                    # 算法对拍台
```

**依赖方向是单向的**：`core` 用 `algo`，`algo` **不**反向依赖 `core`。
所以 `algo` 拿一个 dict 就能跑。

## 五、七个技术点（含代码位置）

> 这一节是给面试和深入阅读用的。**「实现了 X」是技能，「定位 X 的根因是 Y、
> 修复代价是 Z」才是能力。**

### ★★★ 1. 向量检索：症状是「开了但没效果」

**位置**：`agent/qa/retrieval.py:76-90`

**症状**：接上 `nomic-embed-text` 后接口正常返回、索引也建了（4.1MB），
**但排序没有效果** —— 所有卡相似度分数全挤在 0.67 附近，top5 差值 < 0.05。

**为什么这个症状极具欺骗性**：接口不报错、日志不告警、索引文件存在。
任何只看「有没有报错」的检查都会判定这里正常。

**根因**：`nomic-embed-text` 是拿 Matryoshka + 检索任务微调过的模型，
官方用法硬性要求建索引时每条文本前缀 `search_document: `、
查询时前缀 `search_query: `。原实现两边共用同一个函数且**都不加前缀** ——
相当于把查询也编码进文档空间，余弦相似度整个量纲失真。

```python
DOC_PREFIX   = 'search_document: '   # 建索引用
QUERY_PREFIX = 'search_query: '     # 检索用，两边不能合并
```

**修复后的二次问题（这段最值得讲）**：加前缀后索引内容变了，但
**卡片 id 集合没变**，而缓存指纹只按 id 集合算 —— 磁盘上那份**没前缀的坏索引**
被当成有效缓存继续加载。改前缀等于没改，而且**不报任何错**。

```python
def _fingerprint():
    # v2 = 2026-10-03 补上检索前缀。索引内容变了而 card id 集合没变，
    # 指纹必须变，否则磁盘上那份没有前缀的旧索引会被当成有效缓存继续加载
    # —— 改前缀这件事就白改了。以后再动 embedding 输入也照样 +v3、+v4。
    return 'v2|' + '|'.join(sorted(c.get('id', '') for c in _all_cards()))
```

**实测效果**：查「HashMap 为什么线程不安全」，关键词检索 5 条全是
HashMap/LinkedHashMap/ConcurrentHashMap 源码；**向量检索把
「哈希表如何解决冲突与扩容」排到第 2 位**——关键词路径完全漏掉的语义近邻卡。
混合检索 0.296s/次（首建索引 2.9s）。

### ★★★ 2. Louvain 聚合阶段：分母口径错了，症状伪装成「算法失效」

**位置**：`algo/graph.py:294-310`

**症状**：社区发现跑出来后**社区数 == 节点数**，每张卡自成一社区。

**根因**：模块度公式里 `2m` 是「图的总边权」。第一阶段（贪心移动）算对，
但第二阶段会把整个社区聚合成超点，**社区内部的边全部变成自环**。
经典模块度定义里自环按 `2×self` 计入总边权，所以第二阶段的 `2m` **必须重算**。

```python
# ★ 2m 必须每轮重算：聚合阶段社区内部的边变成了自环，
    #   自环按 2×self 计入总边权。第一阶段算的 m2 拿到第二阶段用，
    #   分母偏小 → 所有增益恒为负 → 一个都合并不了，
    #   表现为「社区数 == 节点数，每个节点自成一社区」。
m2l = (sum(w for lst in cur_adj.values() for _, w in lst)
       + 2.0 * sum(cur_self.values()))
```

**修复后**：567 节点稳定收敛为 **17 个社区**（resolution=4.0）。

**延伸取舍**：经典 Louvain 靠随机遍历打破对称，结果不可复现 —— 同一份数据
两次跑可能给出不同分块，测试会间歇性挂，界面上「社区」会莫名变一次。
改成**按 id 排序确定性遍历**，用那点随机性换稳定性。416 节点单线程 < 0.5s。

### ★★★ 3. 图缓存：判断「哪些数据是个人数据」

**位置**：`core/db.py:833-877`

图结构缓存的 key 是 `(category, subject)`。判定「为什么能缓存」时
代码里明确写下了一条约束：

```
★ 为什么能缓存：节点和边完全由 all_cards() 决定，与用户无关
  （level 是 build_graph 里从 progress 贴上去的，属于个人数据，
  不进这个缓存 —— 否则 A 的缓存会被 B 读到，正好是 P0-1 刚修掉的那类 bug）。
```

**关联的坑**：缓存失效判定不能只看 TTL，也不能只看某一个目录的 mtime ——
造卡脚本可能只写 `store` 不碰 `data`。mtime 必须取三个来源的最大值：

```python
def _graph_mtime():
    """卡片数据的最新 mtime。取三个来源的最大值：内置 js、store 目录、data 目录。
    只看其中一个会漏 —— 造脚本可能只写 store，不碰 js。"""
```

### ★★☆ 4. 降级必须可见：静默降级比崩溃更危险

**位置**：`app/main.py:157-161`

**踩过的坑**：`ALGO_STORE=pg` 连不上时，复习记录**静默落进 JSON 文件**；
Redis 连不上时掌握度缓存悄悄退化成进程内存。两种情况启动日志都一片安静 ——
「能跑、没报错」，但数据链路已经不是配置的那个了。

**判断标准**：对依赖可选的系统，「装不上就降级」是对的（不能因为没装 PG
就整个服务起不来），但**降级必须让使用者看得见**。所以三层的 `degraded()`
全部接到启动横幅。

**顺带一条边界**：横幅只打**不依赖登录上下文**的事实。曾想打「今日待复习 N」，
但进度已是 per-user 的，启动时没有登录用户只能读匿名桶（永远为空），
这个数字会显示成「全库卡数」，看着像 bug。个人口径数字交给带 token 的接口。

### ★★☆ 5. 鉴权：判定标准是数据归属，不是 HTTP 方法

**原判定**：按读写操作区分 —— GET 公开、写操作要 token。
**为什么错**：会有「GET 但返回他人学习记录」的接口被漏掉。
**修正后**：`/api/review/due` 这类纯 GET 接口因返回个人复习队列而必须鉴权。

JWT 用 PyJWT 零依赖实现，固定 `algorithms=['HS256']` 防算法混淆攻击。

**更隐蔽的坑**：光给表加 `user_id` 列**不等于**做了隔离 ——
`ON DUPLICATE KEY UPDATE` 只看主键，主键里没有 `user_id` 的话写路径会
**静默覆盖**。`progress` PK 必须是 `(user_id, card_id)`、`notes` PK 必须是 `(user_id, id)`。

### ★★☆ 6. 评测的边界：敢说「我的评测测不出什么」

**位置**：`algo/eval.py`

**结论**：FSRS 效率最优（0.0186），**但没把系统默认切成 FSRS**。

**理由**：仿真评测的 ground truth 是自己造的遗忘曲线 `R(t)=2^(-t/h)`，
它能回答「同一条曲线下谁排期排得好」，**不能**回答「谁对你的学生最好」。
FSRS 排期次数少 20% 是因为它**认为**你记得住 —— 判断偏乐观则实际留存会掉。

**两处主动划清的边界**：
- **BKT 不参与排期对比**：它答「掌握没」不答「何时复习」，硬让它排期是
  塞进不属于它的角色（`eval.py:303` 显式 `continue`）
- **SM-2 根本不预测留存概率**：只有难度因子和间隔，没有概率模型，
  所以 logLoss/AUC 这栏它只能缺席 —— 这不是 bug，是算法真实的能力边界

**实测数据**（300 卡 × 365 天，seed=7）：

| 算法 | 复习次数 | 效率 | 期末留存 | 掌握卡数 | logLoss | AUC |
|---|---|---|---|---|---|---|
| SM-2 | 11783 | 0.0143 | 56.36% | 120 (40%) | 不支持 | 不支持 |
| FSRS | **9455** | **0.0186** | 58.56% | 132 (44%) | 0.738 | 0.529 |
| HLR | 14317 | 0.0139 | **66.52%** | **192 (64%)** | **0.628** | 0.507 |
| BKT | — | — | — | — | 不支持 | 不支持 |

**自我批评**：三者 AUC 都在 0.51 附近（接近随机），说明合成曲线下概率预测
区分度有限。评测价值在排期效率对比，不在概率预测精度。

**双 seed 验证**（结论不翻转 = 可信）：

| 算法 | seed=7 | seed=2026 |
|---|---|---|
| SM-2 | 11783 / 0.0143 / 56.36% | 11846 / 0.0136 / 53.81% |
| FSRS | 9455 / 0.0186 / 58.56% | 10046 / 0.0171 / 57.42% |
| HLR | 14317 / 0.0139 / 66.52% | 13732 / 0.0151 / 68.96% |

### ★★★ 7. 业务缓存：失效靠**内容指纹**，不靠 TTL

**位置**：`agent/qa/retr_cache.py`、`agent/qa/ans_cache.py`、`agent/verify/cache.py`

**要解决的问题**：三个操作的重复代价差了两个数量级 —— 检索 384ms、
校验 60s、生成答案 40~103s（本地 8B）。重复的主要是「同样的输入算同样的输出」，
所以都适合缓存，但**失效条件必须各不相同**：

| 落点 | 实测 | 收益 |
|---|---|---|
| 检索结果 | 384ms → **63ms** | 每次问答跑 1~2 次检索 |
| 校验结论 | 60s → 命中秒回 | 一张卡要联网 + 模型判别 |
| 答案 | 103s → 命中毫秒级 | 本地 8B 出答案要 40~103 秒 |

★ **别凭直觉决定缓存什么，先测**：`due_list`（复习队列）实测只要 **67ms**
（已有 SQL 快路径 LEFT JOIN + 索引），缓存它没有收益；真正的大头是
`retrieval.retrieve()` 384ms。**上表三个落点都是实测后才动的。**

#### 核心决策：key 里放内容指纹，不放时间

```python
# agent/qa/retr_cache.py
def _key(query, k):
    raw = '%s|%s|%s' % (query.strip().lower(), k, library_fingerprint())
    return PREFIX + md5(raw)
```

- **检索用全库指纹**：只含**影响检索**的字段（title/oneLine/keywords/tags/
  mechanism/analogy/subject）。`level`/`nextAt` **不进**——
  你标一张卡不该让全库检索缓存作废。
- **校验/答案用单卡指纹**：字段与 `qa._SHOW_FIELDS` 必须一致，
  漏一个 → 改了那个字段却命中旧结论。

**为什么不用「id + 时间」**：改了卡之后，在 TTL 到期前会一直返回旧结论。
而「卡已改却拿到旧结论」比慢严重得多 —— 前端会拿旧建议去改一张已经被改过的卡。

#### 指纹本身的成本也要算

`library_fingerprint()` 要读一遍全库（`all_cards()` ≈59ms），
每次检索都重算就**把省下的时间又还回去了**。所以它自己带 30 秒短缓存，
用 TTL 换计算：改卡最多 30 秒后反映到检索缓存，这个代价可接受。

#### 答案缓存刻意很保守（正确性优先于命中率）

```python
if not history:                       # ① 有多轮历史一律不查
    hit = ans_cache.get(question, 'flow', web, [])
...
if not sources:                       # ② 检索没命中任何卡才写
    ans_cache.put(question, 'flow', web, [], answer, [])
```

- ① 历史不同答案就不同，命中会**答偏**；
- ② answer 节点**不写 state**，拿不到「用了哪几张卡」就构造不出正确的失效指纹
  —— 那就**宁可不缓存**（纯参数回答不受卡片变动影响，反而最安全）；
- ③ 超长答案（>8000字）跳过，避免占内存；
- ④ 命中时**按 24 字分块吐字**（实测 340 字→14 块），保持流式观感，
  否则前端会突然整段出现。

#### 缓存里只存「指向」，不存「内容」

检索缓存只存 `id + score`，**card 本体每次现取**。所以改了卡片立刻能看到，
缓存不构成「内容陈旧」的来源。库里的卡被删了 → 缓存里那条自动丢掉。

#### ★★ 踩坑：静默失败比不写更可怕

`SearchHit` 是 `__slots__ = ('id','card','score')` 对象，**不是 dict，没有 `.get()`**。
我写 `put` 时用了 `h.get('id')` → `AttributeError` → 被 `except: pass` 吞掉
→ **缓存从来没写进去，却完全静默**。表现是「加了缓存但一点没变快」（实测 0.9x）。

> **规矩：写缓存/读缓存的代码不要裸 `except: pass`**，
> 至少 `print(..., file=sys.stderr)`。否则你永远查不出「缓存没生效」。

同类坑：`card_fingerprint` 原来在循环里对每个 id 调 `db.all_cards()`，
N 张卡 = N×59ms → 改成**一次全量取再查表**（3 张卡 177ms → 59.7ms）。

#### 可分别关闭 + 降级可见

`RETR_CACHE=0` / `QA_CACHE=0` / `VERIFY_CACHE=0` 各自独立。
状态在 `/api/health` 的 `cache.biz.{retr,qa,verify}`，各带
`enabled/backend/degraded/ttl` —— **降级必须可见是项目铁律**。

## 六、算法层

### 间隔重复：4 个算法 + 1 个统一契约

```python
import algo
algo.names()                       # ['bkt', 'fsrs', 'hlr', 'sm2']
algo.get().schedule(prev, level)   # 用默认（sm2）
algo.get('fsrs').schedule(...)     # 临时指定
```

返回值**只能 6 个键**：`level / interval / ef / reps / nextAt / updatedAt`。
多加一个键会被 MySQL 静默丢掉（`progress` 表就是这 6 列，JSON 后端看着好好的、
切到 MySQL 行为就变了）。要加字段先改存储层三处：`core/mysql.py` 的
`DDL_TABLES` + `schema.sql` + `_build()` 的必需表探测。

**换算法优先级**（不用改代码）：环境变量 `ALGO=fsrs` >
`back_study/config.local.json` 的 `"ALGO": "fsrs"` > 默认 `sm2`。
**算法名写错直接抛 ValueError，不静默回落** —— 配置拼错却假装成功，
比启动失败糟糕得多：你以为在评估 FSRS，其实跑了三个月 SM-2。

| 文件 | 算法 | 备注 |
|---|---|---|
| `sm2.py` | SM-2 简化版 | 当前默认，ef 存难度因子（1.3–2.6） |
| `fsrs.py` | FSRS-4.5 | ef 存难度 D（1–10），按记忆稳定性反解间隔 |
| `bkt.py` | 贝叶斯知识追踪 | **含四参数拟合**，不排期 |
| `hlr.py` | 半衰期回归 | 唯一期末留存最高（66.5%），有概率模型 |

**换算法的一个坑**：`ef` 是通用数值槽，SM-2 存难度因子、FSRS 存难度 D。
从 SM-2 切到 FSRS 时旧的 ef 会被当成 D 读，复习几次就回归正常。

### 图算法：6 个

`algo/graph.py` 全部只用标准库（自己写的邻接表，没用 networkx）：

| 函数 | 用途 | 实现要点 |
|---|---|---|
| `pagerank` | 找权威卡 | 阻尼 0.85 是原论文值别调；**悬挂节点秩要均摊回填**，否则孤立卡吞掉全图概率质量 |
| `personalized_pagerank` | 从已掌握卡推荐下一步 | 单次 0.42s，缓存命中 0.055s |
| `betweenness` | 找关键桥梁卡 | 只走 `prereq` 边 |
| `louvain` | 社区发现 | 见上文 ★★★2；**必须用全部边**（含 belong 骨架），否则 416 张卡只有稀疏 related 会碎成单点 |
| `shortest_path` | 两卡之间最短学习路径 | 走先修边 |
| `kcore` | 剥层级，找出核心骨架 | k=2 |

**PageRank vs 度中心性**（为什么这页值得存在）：degree 数的是「我连着几个知识点」，
PageRank 数的是「连着我的知识点有多重要」。一张连接 10 张废卡的卡 degree 很高
但 PageRank 很低。**造卡产生的 related 关系有噪声，PageRank 比度数抗噪。**

`analyze()` 一次跑完中心性+社区+体检，`topn()` 取前 N，`coverage()` 看边类型分布。

## 七、两个 Agent

### 问答 Agent（`agent/qa/`）

**两种模式**（**两个都流式**）：

| 模式 | 入口 | 说明 |
|---|---|---|
| `flow` | `qa_app()` / `stream_flow()` | 固定流程：检索 → 拼上下文 → 一次 LLM 调用。快、稳、便宜 |
| `react` | `react_app()` / `stream_react()` | ReAct 循环：模型自己决定调哪个工具、调几次。可联网 |

```python
runtime.ask_full(question, mode='react', history=[], profile={},
                 on_sources=cb, web=True, user_id=uid)
runtime.stream_react(question, hist, prof, on_sources=on_sources,
                     web=web, user_id=uid)     # ★ 参数名是 user_id 不是 uid
```

#### ★ 为什么 flow 也能流式（这是本项目绕得最远的一个坑）

flow 的 answer 节点原来是 `M.chat().invoke()` **一次性返回**，本地 8B 要
20~40 秒空白 —— 用户盯着空白只能判断「坏了」。改成流式需要解决两件事：

**① LangGraph 节点函数只能收到 state**，没法多传一个 `on_token` 参数。
用 **ContextVar** 绕过去（和 `tools.set_current_user` 同一套路）：

```python
# agent/qa/nodes.py
_on_token = ContextVar('qa_on_token', default=None)

def answer(state):
    sink = _on_token.get()
    if sink is None:                      # 没装 → 老路径，行为完全不变
        return {'answer': M.chat().invoke(msgs).content, ...}
    buf = []
    for piece in M.chat().stream(msgs):  # 边生成边往外发
        buf.append(piece); sink(piece)
    return {'answer': ''.join(buf), ...} # state 仍等完整生成后才写
```

**② 同步回调里不能`yield`**。SSE 层用**后台线程生成 + 队列转发**：
sink 塞队列，外层排空后 yield。

> ★ **流式不改质检**：flow 也有 `grade` 自检，它拿到的仍是**完整**答案，
> 没过检照样重写一轮 —— 所以用户可能看到答案被覆盖重写，这是设计如此。
> （如果把半截内容提前交给质检，它会对着残缺答案打回，然后无限重试。）

实测：444 帧正文、出字跨度 **103.67s**（首帧 0.1s）—— 真流式而非攒完再发。

#### SSE 帧协议（改了必须两边同步）

| 帧 | 含义 |
|---|---|
| 无 event 名 | 正文增量（换行转义成 `\n`） |
| `event: step` | `{text}` 新增一步/ `{text:'',done:true}` **只收尾** |
| `event: sources` | 引用到的卡片 id（必须在 done 之前发） |
| `event: verify` | 卡片校验建议（有错才发） |
| `event: done` / `event: error` | 结束 / 出错 |

**★ 每个新增 step 必须有一次收尾帧**。漏了的表现是
**答案全文都显示了、步骤条还在转圈且永不消失**（实测踩过）。`except` 分支也要补。

**7 个工具**（`tools.py`，docstring 直接作为模型可见的接口契约）：

| 工具 | 作用 | 来源 |
|---|---|---|
| `search_cards` | 卡片检索 | 内部 |
| `card_detail` | 单卡详情 | 内部 |
| `related_cards` | 关联卡 | 内部 |
| `due_today` | 今日待复习 | 内部 |
| `web_search` | 联网搜索 | MCP `web-search` |
| `run_python` | 代码沙箱 | MCP `code-exec` |
| `github_search` | 找代码示例/学习路线 | MCP `github-resource` |

（第 8 个 `generate_card` **刻意不进每轮问答**——属「内容生产」动作、
调用重，qwen3:8b 工具一多就选错。它由导入流程或另一个 Agent 直调。）

**用户身份怎么传**：工具签名**不能带 user_id**（要暴露给模型看），
所以用 ContextVar：

```python

# 工具内部 tools.current_user() 读
```

⚠️ **ContextVar 不跨线程**。子线程里读到 `None`，现在靠「同线程碰巧能传」。

**联网**（`websearch.py`）：走 360 搜索，**免 key**，失败返回 `[]` 不抛异常。

**混合检索带缓存**（`retrieval.retrieve()`，实测 384ms → 63ms）：
缓存只存 `id + score`，card 本体每次现取 → 改卡立刻生效。详见技术点 7。

### 造卡 Agent（`agent/cards/`）

四阶段流水线，**graph 只负责流转、runtime 负责落盘、router 定 HTTP**：

```
文档 → LLM 定切分点(structure/refine/chapter) → 近重标题去重(dedup.py) → 草稿池
```

- 卡片 id = `ag-` + md5(docId:idx)
- `dedup.py` 解决「近重标题」：LLM 切出来的标题经常高度相似，
  需要按语义相似度合并而不是按字符串判等

### 卡片校验 / 自纠 Agent（`agent/verify/`）

**业务动机**：库里的卡是模型生成的，会过时/有错。用户问一个知识点时，
除了回答，**顺带核对这次引用到的卡**；有错就在聊天流里反问
「要不要按最新资料修正这张卡」。

```
react 答完 → 取引用到的前 2-3 张卡
  → 逐张联网取证（web_search + github_search）
  → 一次批量 LLM 判别（_judge_batch）
  → 只返回 proposed_patch 非空的 → event: verify → 前端渲染字段diff
  → 用户点了才 POST /api/agent/verify/apply → db.apply_card_patch
```

#### ★ 绝不自动改知识库

自动落库等于「AI 偷偷改知识库」，错了难追溯。所以后端**只产出建议**，
落库必须由用户点确认触发。前端有「应用 / 忽略 / 还原」三个动作。

#### ★ 修正内置卡为什么用「覆盖层」而不是改源码

那 416 张内置卡在 `data/*.js` 里是只读的，`update_card` 直接 404。
最初实现成「把内置卡复制成**同 id** 自定义卡去覆盖」，实测**内置卡凭空消失**
（412→411）—— 因为 MySQL `cards` 表**主键只有 `id`、没有 `(id,origin)`**，
`ON DUPLICATE KEY` 命中 id 主键把内置卡行静默覆盖了
（与「光加列不改主键 = 没隔离」是同一类坑）。

正解：**覆盖层** `data/store/cards.override.json`（id → patch），
`all_cards()` 读取时叠加。**不动原始卡、不进 cards 表、可一键还原**。

#### 性能：批量 vs 逐张，以及不阻塞 UI

- **逐张判别**每张卡喂一遍「整卡+ 联网」给模型 → 3 张近 **300 秒**，聊天没法用
- 改**批量**一次调用 → 实测 **60 秒**（联网仍逐张搜，保证每卡有真实证据）
- 再加**结果缓存** → 命中秒回
- **`done` 帧先发**：校验放done 之后跑、结果作 `verify` 帧补发，
  绝不让校验把「答案已出」这件事卡住几分钟

校验发生在答案**已经显示之后**，所以 step 帧标 `kind:'bg'`——
前端渲染成一行**呼吸点**而不是转圈（转圈会让人以为"还没答完"，实测反馈）。

### 一条必须记住的通则

> **同一页面里，图和图的统计必须来自同一次筛选。**

前端最常见的错误写法是「指标是全库口径的，切筛选不重拉」——听起来合理，
实际会让所有「用节点表反查指标」的逻辑全盘失效。

**判断法**：只要前端有任何一处拿 A 的结果去查 B 的 id 集合，
A 和 B 就必须来自同一次计算、同一套编码。

真实踩过的坑：社区洞察只在首次进入时拉一次、且是全库口径，
于是 `communityName` 拿「筛后的 nodes」去查「全库的 members」，
一个 id 都对不上 → **15 个社区 13 个显示「（空）」**。

   无单测覆盖；`uid=` vs `user_id=` 一个词的差别让流式问答 100% 挂，
   而非流式正常 → 症状是「flow 能问、react 不能」，极易误判成模型问题
2. **`res.json()` 会吃掉真错误信息**：响应体为空时 `JSON.parse` 抛
   `Unexpected end of JSON input`，把后端给的人话原因全盖掉。
   → 错误分支改 `res.text()` 再 try-parse
3. **静态分析是盲区**：`rt` 是 `_runtime()` 动态拿的，写扫描器查参数名匹配
   一个都查不到。半成品扫描器比没有更糟 → 改用签名逐个核对
4. **探针必须打真实 HTTP**：直调 `db.*` 绕过路由层和静态回落，验不出路由 bug
5. **造探针数据要从库里捞**：`java-hashmap` 这个 id 在 416 张卡里根本不存在，
   编造 id 会伪装成「后端没修好」
6. **Git Bash heredoc 会被安全策略拦**且路径被改写，写文件一律用 Write 工具
7. **`taskkill //PID` 在 Git Bash 里会被当路径**，杀进程用 PowerShell 的
   `Stop-Process -Id <pid> -Force`
